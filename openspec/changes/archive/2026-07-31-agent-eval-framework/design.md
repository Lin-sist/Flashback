## 2. 评测怎么挂（架构）

### 2.1 三层结构

```text
┌─ 用例文件（数据） ────────────────────────────────┐
│  backend/src/test/resources/eval/cases/*.yaml      │  入库：合成样例
│  backend/src/test/resources/eval/samples.local.yaml│  本地：真实样本（gitignore）
│  backend/src/test/resources/eval/baseline/*.yaml   │  入库：快照 + baselineNote
└────────────────────────────────────────────────────┘
                     │ 参数化 runner 读取
                     ▼
┌─ harness（装配 + 驱动） ──────────────────────────┐
│  纯 Mockito 装配 AgentChatServiceImpl（22 个协作者）│
│  scripted AgentModelClient 替身（按轮次编排响应）    │
│  @Mock AgentTraceSink → 拦下 persist，拿到收集器     │
│  驱动 service.sendMessage(...) 一到多轮             │
└────────────────────────────────────────────────────┘
                     │ 产出 AgentTraceCollector（内存）
                     ▼
┌─ 断言（两层，失败语义不同） ──────────────────────┐
│  不变量层：硬失败，无刷新手段                       │
│  快照层：失败 = 需人确认，手工更新 + 改 baselineNote │
└────────────────────────────────────────────────────┘
```

**关键点：断言对象是轨迹信号，不是最终回复文本。** 这是架构宪法 §3.6 的明文要求，也是本刀能在 mock 路径下仍然有意义的唯一原因——回复文本的好坏 mock 说不了话，但「阶段推进对不对、注入了几条、护栏判了什么、降级发生在哪层、回复被裁了多少」这些全是编排逻辑的产物，与模型语言能力无关。

### 2.2 为什么不需要碰 main 代码

四条事实叠起来刚好够（proposal E9 / E11 / E12 / E16）：

1. `AgentChatServiceImpl` 22 个协作者**全部构造注入**，单一 public 构造 → harness 可整套装配。
2. `AgentTraceCollector` 的**全部读取器已 public**（含 `steps()`）→ 不需要新增 getter。
3. `AgentTraceSink.persist(collector)` 是**唯一出口** → `@Mock` 它就能用 `ArgumentCaptor` 拿到收集器，且不落库。
4. junit-params 与 snakeyaml **已在测试 classpath** → 不改 pom。

这四条不是运气，是 C5 决策 2「收集器 + 单一落库出口」与 C1 以来的构造注入纪律的副产品。C5 当时的理由是「埋点不能散落」，现在它顺带让 C6 白拿一个断言入口。

### 2.3 快照文件的形状（示意，非最终格式）

```yaml
# baseline/restraint.yaml
- caseId: emotion-first-turn
  baselineNote: "C6 定基线；policyVersion=gc03e94cf；promptVersion=pea5c33ea"
  snapshot:
    stagePath: [EMOTION]
    stageReasons: [ADVANCE]
    providerCalls: 1
    injectedCount: 0
    injectedChars: 0
    downgradeLayer: null
    replyLength: 14
    replyToInputRatio: 0.7
```

**没有一个字段承载文本。** 快照里只有枚举短标识、计数、长度、比例。这不是靠自觉——C5 已经把「收集器只接受基础类型与既有枚举」在类型层钉死了（`step(...)` 是私有可变参数入口），C6 的快照从一个本来就不含文本的对象派生，天然继承这个性质。验收 21 的测试是对这条性质的机械复核，不是唯一防线。

## 3. 决策记录

### 决策 1：评测跑在什么基座上（N2）

1. **面临的选择**：(a) 纯 Mockito harness，拦 `AgentTraceSink` 拿内存中的收集器；(b) `@SpringBootTest` + H2，评测跑完从 `agent_turn_trace` 表读回轨迹再断言；(c) 两者都做，前者跑不变量、后者跑落库正确性。
2. **选了哪个 + 为什么**：**推荐 (a)**。三条理由，第三条是决定性的：① 范式已存在——`AgentGuardrailTraceCorrelationTest` 就是纯 Mockito 驱动完整 `sendMessage`，C6 不需要发明新做法，只需要把它的装配抽成可复用 harness；② 速度决定这个资产会不会真的被跑，Spring 上下文启动成本会让「每次改动都跑一遍」退化成「记得的时候跑一下」，而本刀存在的意义就是不再依赖有人记得；③ **走 DB 路线要额外驯服一条反直觉约束**——`AgentTraceSink.persist` 用 `TransactionSynchronization.afterCompletion` 落库（C5 修 50 秒锁等待的产物），因此 C5 的集成测试**刻意不能加 `@Transactional`**，得手工清理数据。为「断言编排信号」这件事付这个成本，零增量价值。
3. **放弃的代价**：(a) 评不到「轨迹落库是否正确」——但那本来就不是 C6 的问题，C5 的 `AgentObservabilityIntegrationTest` 已经覆盖，重复做等于把别人测过的东西再测一遍。(c) 的代价更具体：它会让评测套件的运行时间跟着 Spring 上下文走，而且要维护两套装配；等真出现「落库丢字段」这类问题时再补一条集成用例，成本远低于现在就上两套。

### 决策 2：可编排替身挂在哪一层（N3，P8 的答案）

1. **面临的选择**：(a) scripted `AgentModelClient` 替身——stub `isMockProvider()=false`，按轮次编排 `completeWithTools` 的返回序列；(b) 直接改 `AgentMockResponder` 让它能产出违规；(c) 为 `AgentMockResponder` 抽一个接口，生产用现有实现、测试用可编排实现。
2. **选了哪个 + 为什么**：**推荐 (a)**。(b) 先被规则排除：`AgentMockResponder` 是 `@Component`，在 mock provider 下**跑在生产路径上**，改它就是改生产行为——这与 C5「不为可观测改行为」是同一条纪律，蓝图 §4.2 也已明文禁止。(a) 与 (c) 的分野是本刀规划里最容易选错的一处：(c) 看起来更正统（面向接口、不碰 `AgentModelClient` 这个具体类），但**它覆盖不到上下文组装**——`generateReply` 在 `if (modelClient.isMockProvider())` 处直接 return，mock 分支**根本不组装 prompt**，因此走 (c) 的评测永远看不到 `prompt` 步骤，也跑不出「因为 prompt 少了记忆补充段而导致的问题」。(a) 强制走非 mock 分支，八个维度里的上下文组装、全部降级路径、工具提议被拒、provider 失败四类才有落点。
3. **放弃的代价**：(a) 要 mock 一个具体类而非接口，理论上比面向接口"脏"。实际代价接近零——既有测试早就在 `@Mock AgentModelClient`（`AgentChatServiceImplTest`、`AgentGuardrailTraceCorrelationTest` 都是），Mockito 对非 final 具体类没有障碍。真正的代价是替身要自己拼 `AgentModelResponse`（content + toolCalls），比调 `AgentMockResponder` 的现成文案麻烦一点——但这恰恰是想要的：**能拼出违规内容才是替身的全部价值**。(c) 的额外代价是它会为了测试给 main 加一个接口，撞「零 main 改动」这条本刀最大的安全优势。

### 决策 3：快照能不能一键刷新（N4）

1. **面临的选择**：(a) 只能手工编辑快照文件，且必须同步更新 `baselineNote`，由测试强制；(b) 提供 `-Deval.snapshot.update=true` 自动重写全部快照；(c) 自动重写 + 要求人事后补 `baselineNote`。
2. **选了哪个 + 为什么**：**推荐 (a)**。这是本刀唯一一处**故意增加摩擦**的设计。理由是失效路径太好预测：有了 `-Dupdate`，「评测红了」这件事的最短解决路径就从「停下来想想这个变化对不对」变成「跑一下命令让它变绿」，那么整套框架就退化成一个耗时的空转——它仍然会失败，但失败不再传递任何信息。(c) 的「事后补说明」在任何团队实践里都等于不补，因为绿灯已经拿到了，补说明变成纯负担。手工编辑的摩擦在这里是特性：它让「更新基线」保持为一个需要判断的动作。
3. **放弃的代价**：用例多了以后批量更新会烦，尤其一次改动同时影响十几条快照时。缓解有两条：① 失败信息直接打印可粘贴的新值，人只需确认后粘贴；② 若将来真的烦到影响使用，那时再加开关是有依据的决策，且届时应当配一条「`baselineNote` 未变更则失败」的守护——但**不要现在就先给出口再补守护**，那个顺序在实践中永远是出口先落地、守护永远在待办里。

### 决策 4：`baselineNote` 靠约定还是靠测试（防橡皮图章的落地方式）

1. **面临的选择**：(a) 只在文档与 review 里要求「改快照必须改说明」；(b) 加一条测试，机械校验「快照数值与 `baselineNote` 的一致性」；(c) 用 git hook / CI 检查 diff。
2. **选了哪个 + 为什么**：**(b)**，且这条测试本身就是本刀的一个交付物（验收 19）。理由是本项目已经有过一次"靠自觉维持边界"的反例讨论——蓝图 §9.6 拒绝「仅内存不落盘的精细诊断载体」，明确的理由就是"靠后人自觉维持隐私边界，半年后有人为排查方便把它塞进 trace，红线就破了且无测试报警"。同一个逻辑适用于 `baselineNote`：一个只写在文档里的约定，在某个赶时间的下午必然被跳过。(c) 被排除是因为仓库当前**没有 CI**（proposal E20），git hook 又是本机配置、不入库、换机即失效。
   具体实现方向：快照条目里存一个由「快照数值 + `baselineNote`」共同派生的校验值，改了数值不改说明则校验值对不上——**这与 C5 决策 6 拒绝手工 bump 版本号是同一个手法**（把「人必须记得同步」变成「不同步就报错」）。
3. **放弃的代价**：多一层机制，且这层机制自己也需要被测。接受它的理由是：本刀的核心价值主张就是「量尺不会骗人」，而橡皮图章是量尺骗人的**主要形态**——防它的机制不能比它更脆弱。(a) 的代价是最坏的：文档写得很漂亮，半年后没人记得，而且**没有任何信号告诉你它已经失效了**。

### 决策 5：本地真实样本的命名与忽略规则（N5，偏离已冻结蓝图写法）

1. **面临的选择**：(a) 按蓝图 §4.2 原文命名 `local-samples.yaml`，`.gitignore` 加 `**/local-samples.yaml`；(b) 改名 `samples.local.yaml`，`.gitignore` 加通配 `*.local.yaml`。
2. **选了哪个 + 为什么**：**推荐 (b)，但因偏离已冻结蓝图的写法须您裁决。** 决定性理由是本仓库刚为这件事付过学费：C5 把 `.gitignore` 从「只点名 `start-dev-wechat.local.ps1`」改成通配 `*.local.ps1`，原因写在 `.gitignore` 的注释里——「原先只点名 start-dev-wechat.local.ps1，新增的本地脚本不会被覆盖」。(a) 会原样重犯这个错：将来若把样本按维度拆成第二个文件（很可能，因为八个维度的样本混在一个文件里会很难读），新文件不在规则内，而漏出去的东西是**用户真实日记**——这是本仓库隐私等级最高的一类数据。(b) 让「凡 `.local.` 的样本一律不入库」成为规则而非逐个登记，同时与既有 `*.local.ps1` / `/backend/*.local.env` / `/frontend/.env.*.local` 的命名习惯一致。
3. **放弃的代价**：与已冻结蓝图的字面写法不一致，须在本 change 登记为一处偏离（因此单独成条请示，不自行决定）。另有一个真实的次生风险：通配 `*.local.yaml` 会把**任何**以 `.local.yaml` 结尾的文件挡在版本控制外，将来若有人想入库一个 `something.local.yaml` 会困惑——缓解是复用仓库既有的放行惯例（`!/backend/secrets.local.env.example` 那种 `!` 前缀），需要时显式放行。

### 决策 6：用例文件用什么格式解析（N1）

1. **面临的选择**：(a) YAML，直接用 snakeyaml（`spring-boot-starter` 的传递依赖，已在测试 classpath）；(b) YAML，新增 `jackson-dataformat-yaml` 依赖；(c) JSON，复用已声明的 jackson-databind。
2. **选了哪个 + 为什么**：**推荐 (a)**。用例文件是**要被人读和 review 的资产**，里面装的是中文用例、多行输入、以及解释「这条用例在测什么」的注释——JSON 不支持注释，多行中文字符串在 JSON 里也难读，(c) 会让这批资产的可维护性明显下降。(b) 要动 `pom.xml`，撞 `AGENTS.md`「不改 package / lockfile 除非任务明确要求并说明原因」，而它换来的只是一层 API 糖（`ObjectMapper` 风格的绑定），snakeyaml 直接 `load` 成 `Map` / `List` 对这个用量完全够。
3. **放弃的代价**：snakeyaml 是**传递依赖而非本项目直接声明**，理论上未来某次 `spring-boot-starter` 升级可能把它移除（Boot 4.x 是代际重置，这不是纯理论担忧——见蓝图 §4.6）。这个代价必须被显式缓解，否则某次升级后评测会静默变成"跳过全部用例"，而那正是最坏的形态：**绿灯但什么都没测**。缓解是硬性的——解析器不可用时**明确失败**而不是跳过（验收 3）。若那天真的到来，换 JSON 或补依赖是局部改动，成本远低于现在就为它多背一个依赖。

### 决策 7：为什么不做 LLM-as-Judge（out_of_scope 边界，D31）

1. **面临的选择**：(a) 不做，改用「轨迹不变量 + 快照回归 + 人评锚点」；(b) 做一个 Judge，把回复送第二个模型打分；(c) 折中——只对本地样本跑 Judge，合成用例不跑。
2. **选了哪个 + 为什么**：**(a)**，这是蓝图 D31 已冻结的决策，本刀执行它。三条理由各自独立成立：① **隐私**——日记原文送第二个模型属未授权外发，意味着每跑一次评测都要走闸门 3，而「每次改动都能跑」是本刀的核心价值，两者直接矛盾；② **预算**——本项目真实调用的历史量级是「6 次 / 预算 10」，Judge 跑几十条用例即爆表；③ **不可复现**——同一份输入两次打分可能不同，而架构宪法 §3.6 明确要求「维度稳定」。(c) 看起来聪明，实际是最糟的：它把 Judge 的三个问题全保留（本地样本恰恰是真实日记，隐私问题最重），只换来"合成用例便宜"这个本来就不是问题的好处。
3. **放弃的代价**：**语言质量真的评不了。** 这是本刀必须诚实承认的边界，不能含糊——用替身跑评测，评的是编排逻辑，不是模型的语言能力。对应的处置是把这句话写进 spec 与叙事文档：「Eval 覆盖轨迹不变量与回归比对；语言质量靠真实探针小样本人评锚定，没有假装用 Judge 覆盖它。」这条边界如果不写清，本刀就变成一个"看起来测了质量其实没测"的资产——那比没有它更危险，因为它会让人误以为改 prompt 是安全的。

### 决策 8：话术质量维度做到哪一步（N7）

1. **面临的选择**：(a) 只建结构——定义人评锚点文件的形状，入库空模板 + 说明，真实锚点走本地文件；(b) 本刀就填入真实锚点样本；(c) 本刀完全不碰这个维度，等 C7 再说。
2. **选了哪个 + 为什么**：**推荐 (a)**。(b) 需要真实 provider 产出 + 人工评判，属闸门 3 范围，而本刀申请 0 外调（决策 9）。(c) 会让蓝图 §4.2 的八维度表少一维，更要紧的是「语言质量靠人评锚定」这句承诺会变成一句没有落点的话——半年后回头看，会分不清是"决定不做"还是"忘了做"。(a) 的产物是结构就位、界划清楚、锚点待填，**并在文件里如实写明它现在是空的**。
3. **放弃的代价**：交付一个空结构有"占位符工程"的味道，且空文件容易被误读成"这个维度已经覆盖了"。缓解是**在文件与 spec 里都显式标注锚点为空**（验收 15），并写清它的填充时机：建议顺带在 C7 的闸门 3 里做——C7 必然要真实联调重写路径，同一批真实产出既验重写效果又能当锚点，比现在单独申请一轮外调更省。

### 决策 9：为什么本刀不申请闸门 3（N8）

1. **面临的选择**：(a) 不申请，预算 0；(b) 申请 ≤6 次真实调用，用于填 N7 的人评锚点并验证快照指标在真实 provider 下的稳定性。
2. **选了哪个 + 为什么**：**推荐 (a)**。C6 交付的是量尺本身，而量尺是否正确**用替身就能验**——不变量对不对、快照机制会不会被绕过、隐私断言能不能拦住泄漏，这些全部与真实模型无关。真实调用能回答的只有两件事：人评锚点长什么样（可推迟，见决策 8）、快照指标在真实 provider 下稳不稳（对本刀无用，因为快照的设计前提就是跑在确定性替身上，真实 provider 下指标本来就会波动）。为这两件事单独申请一轮外调，性价比不成立。
3. **放弃的代价**：`unknown` 项多一条——快照指标在真实 provider 下的稳定性未验证（proposal E36）。这个代价必须**如实登记而不是回避**，因为「按 Phase 1 的习惯每刀都跑闸门 3」会让人默认本刀也验过。它其实不构成风险：快照的用途是"同一份确定性输入下，改动前后是否变化"，真实 provider 从来不在这个用途里。

### 决策 10：为什么不顺手校准那条明标「未校准」的阈值（out_of_scope 边界）

1. **面临的选择**：(a) 不校准任何阈值；(b) 顺手校准 `minMemoryOnlyRunForAttribution`（代码注释明写"未经真实样本校准"，而本刀刚好在建能支撑校准的量尺）；(c) 校准并把校准前后的对比作为本刀"量尺有用"的证明。
2. **选了哪个 + 为什么**：**(a)**。(c) 尤其诱人——它能给本刀一个漂亮的收尾故事。但它会毁掉本刀最有价值的一个性质：**基线的纯净**。C6 交付的基线必须记录"当前状态"，一旦本刀自己改了阈值，基线就变成"C6 调过之后的状态"，那么将来任何人想问"C6 之前 Agent 是什么样"都没有答案了。更实际的问题是归因：阈值和量尺一起改，指标动了以后分不清是量尺算错了还是阈值改对了——这正是 R2 那次误判的同型错误（两个变量一起动，把功劳记在错的那个上）。
3. **放弃的代价**：E27 那条未校准的阈值继续挂在残余里，多等一刀。这个代价很小且明确：它已经挂了一段时间，再挂一刀不会更糟，而校准它需要的量尺本刀正在建——**下一刀做它是有依据的，本刀做它是没依据的**。

### 决策 11：为什么不顺手建 CI（out_of_scope 边界）

1. **面临的选择**：(a) 不建，如实记录仓库无 CI、本刀交付"一条 maven 命令可跑"；(b) 顺手加一个 GitHub Actions workflow 让评测有真正的门槛；(c) 加 git hook 在本机拦。
2. **选了哪个 + 为什么**：**(a)**。架构宪法 §3.6 写着 `EvalPort` 必须「CI 可跑子集」，而实测仓库**没有 CI**（无 `.github/`，workflow 零命中）。这里有两条路：把宪法那句话兑现（建 CI），或如实承认它当前没有落点。选后者的理由是建 CI 撞 `AGENTS.md`「不改 deployment / monitoring」，且它是一个独立决策——涉及跑在哪、密钥怎么给、失败怎么处理，塞进一个评测 change 里做等于绕过决策。(c) 不入库、换机即失效，是伪解决。
3. **放弃的代价**：评测**没有强制力**——它会在 `mvn -q test` 里跑，但没有任何机制阻止有人在红着的情况下继续。这个代价必须写进验收（验收 34）而不是含糊过去，否则文档会给人"已经有门槛了"的错觉。缓解是本刀选 N6（评测就是普通测试，不做门控），至少它跑在默认路径上，不需要有人记得单独跑。

### 决策 12：为什么不改既有那条子串式隐私断言，而是新写一条结构化的

1. **面临的选择**：(a) 既有 `verdictMetricsMustNotLeakContent` 原地不动，C6 新增结构化格式校验；(b) 把既有那条改成结构化的；(c) 只依赖既有那条，C6 不新写。
2. **选了哪个 + 为什么**：**(a)**。(b) 违反蓝图 §4.2 与 `AGENTS.md` 的既有断言零修改纪律——那条断言是 C4 的交付物，改它就要在 C6 的 diff 里混进护栏资产的改动。(c) 不行，因为既有那条是**负向子串断言**（`doesNotContain("软件工程", ...)`），它只能守住当初那几个词：换一批用例文本、或某天实现里不小心把别的文本塞进指标串，它一声不响就放过去了。而 `AgentGuardrailVerdict.metrics()` 的格式按构造只含数字（`coverage=%.3f maxUncoveredRun=%d checkedLength=%d`），完全可以断言"整串必须匹配这个纯数值形状"——那是白名单式断言，比黑名单强一个量级。
3. **放弃的代价**：同一个隐私性质有两条测试守着，看起来重复。这个重复是可接受的：既有那条是 C4 的历史资产（它证明的是"C4 当时确实检查过这件事"），新那条是 C6 的守护。删旧的会丢历史，改旧的会破纪律，留着并加强是唯一不损失东西的做法。

## 4. 验证策略

| 层 | 怎么验 | 失败语义 |
|---|---|---|
| 不变量（八维度的确定性部分） | 参数化 runner 跑用例 → 断言收集器的步骤序列与数值 | **硬失败，无刷新手段** |
| 快照 | 同上，比对 `baseline/*.yaml` | 需人确认；手工更新 + 改 `baselineNote` |
| 防橡皮图章机制自身 | 构造「只改数值不改说明」的输入，断言它**被拦住** | 硬失败（验收 19） |
| 隐私 | 结构化格式校验（指标串必须是纯数值形状）+ 快照文件不含用例文本 | 硬失败（验收 21–22） |
| gitignore 规则 | `git check-ignore` 对样本文件路径返回命中 | 硬失败（验收 23） |
| 零 main 改动 | `git diff --stat` 中无 `src/main` 条目 | 硬失败（验收 28） |
| 既有资产 | `mvn -q test`：534 PASS / 3 skipped，既有断言零修改 | 硬失败（验收 36） |
| 真实 provider 下稳定性 | **不验**，如实记 `unknown`（E36 / 决策 9） | — |

**验证顺序上的一处硬约束**：`.gitignore` 规则必须在真实样本文件存在**之前**落地（实现顺序第 2 步）。颠倒的后果不可逆——一旦真实日记进了 git 历史，删文件也删不掉历史里的内容。
