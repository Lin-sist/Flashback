# Design：Agent Review Chat（C3 后半刀）

> Change ID：`agent-review-chat`
> 阶段：**规划闸（闸门 1）—— N1–N6 已定稿（2026-07-29 用户按推荐批准）**
> 本文件按用户要求只保留**决策记录**，不铺展架构图与数据流——共享部分与 C1/C2/C4/C3a 完全一致，差异全部记在下面的决策里。

---

## 定稿摘要

| # | 定稿 |
|---|---|
| N1 | 同一 `AgentChatServiceImpl` + purpose 分支，**差异收敛到单一模式判定点** |
| N2 | `stage` 用专用常量 `REVIEW`；结束 = 轮次上限或用户 `finish`；轮次上限单列配置，默认 6 |
| N3 | 注入 `content` + `ai_summary` + `belief_then`，**全部进 MEMORY 层** |
| N4 | 时间归属阈值**不动**，靠合并联调实测；不为回看单开阈值，不在回看关掉该检查 |
| N5 | 复用 `POST /api/agent/sessions`，请求体加 `purpose`（缺省 `WRITING_GUIDANCE`） |
| N6 | `selectActiveByUserAndRecord` 补 purpose 谓词 |

---

## 决策记录

### 决策 1：回看与写作引导是同一条链路还是两条

1. **面临的选择**：(a) 同一 `AgentChatServiceImpl`，按 `session.getPurpose()` 分支；(b) 新建 `AgentReviewChatServiceImpl`，复用 mapper/PromptBuilder/护栏/MemoryPort 但自己实现开会话与轮次；(c) 抽 `AbstractAgentChatService` 模板，两个子类实现差异。
2. **选了哪个 + 为什么**：**(a)**，并附一条硬约束——四处差异（开会话校验、轮次推进、工具上下文、素材生成）必须收敛到**一个显式的模式判定点**，而不是散落四个 `if (purpose == REVIEW_CHAT)`。决定性理由是护栏不能分叉：回看同样要过忠实度、诊断、代决、伪引用、时间归属五层，(b) 会让这五层在两条链路各接一遍，下次改护栏必然漏一边——而「护栏规则分散在多处」正是 C4 决策 5 花力气修掉的问题，不该在这里重新引入。
3. **放弃的代价**：(b) 的代价是失败重试语义、归属校验、护栏接入顺序出现两份相似代码，长期维护成本高于省下的分支复杂度。(c) 的收益要等到第三种 purpose 出现才兑现，但代价是现在就要重构 C1/C2/C4 已验收的编排骨架，触碰 `AGENTS.md`「不做大规模 backend rewrite」，且重构风险由本刀承担。

### 决策 2：回看会话的 stage 存什么

1. **面临的选择**：(a) 固定存 `OPENING`；(b) 固定存 `CLOSING`；(c) `AgentStage` 新增专用常量 `REVIEW`。
2. **选了哪个 + 为什么**：**(c)**。`stage` 列是 `VARCHAR(30)`，加枚举值不需要 DDL。选专用常量的理由是可读性与可排查性：数据库里看到 `REVIEW` 就知道这是回看会话，而 `OPENING` 会让人以为回看也有阶段推进只是卡在第一阶段。另外 `CLOSING` 在写作引导里是**会触发素材生成**的阶段（`sendMessage` 里 `targetStage == CLOSING` 即调 `generateMaterial`），复用它等于给自己埋一个「回看意外产出素材」的坑。
3. **放弃的代价**：新增枚举值要检查既有 `switch`（`stageGoal` / `buildTurnInstruction` / `AgentStageMachine`）是否需要补分支——这是一次性成本，且编译期能发现遗漏（Java switch on enum 有覆盖检查的地方会报错，没有的地方走 default）。相比 (b) 那个隐蔽的素材陷阱，这个代价更可控。

### 决策 3：回看对话读哪些字段

1. **面临的选择**：(a) 仅注入记录正文 `content`；(b) `content` + `ai_summary` + `belief_then`；(c) 再加 `reality_later` + `reply`。
2. **选了哪个 + 为什么**：**(b)**。这三个字段都是「用户在封存那一刻的表达与当时的整理」，时间语义统一——都属于「那时候」。回看对话的核心是帮用户理解那时的自己，这三样足够。
3. **放弃的代价**：(c) 里的 `reality_later`（后来其实）与 `reply`（解锁后的回应）是用户**解锁之后**写的，与 `content` 不在同一个时间点上。把它们和三个月前的正文混进同一层来源，Agent 就可能把「后来写的感想」当成「那时的想法」复述，而时间归属检查只区分「会话层 / 记忆层」，区分不了记忆层内部的两个时间点。这个风险不值得为多两个字段承担，留给后续需要时单独处理。

### 决策 4：注入的记录内容进哪一层来源

1. **面临的选择**：(a) 进 SESSION 层（视作「用户自己的话」）；(b) 进 MEMORY 层（视作「过去的表达」）。
2. **选了哪个 + 为什么**：**(b)**。这条记录的正文确实是用户自己写的，但**是三个月前写的**。放进 SESSION 层会产生一个具体的坏结果：Agent 复述那时的话时**不需要**带时间归属，于是「你觉得撑不住」这种句子读起来就像用户此刻说的——而这正是 C3a 花整个护栏去防的事。放进 MEMORY 层后，Agent 必须说「你那时写的」，这恰好就是回看该有的说法。
3. **放弃的代价**：代价很实在——回看对话里几乎**每一轮**都会触发时间归属判定，而该阈值未经真实样本校准（R8）。误伤会让 Agent 频繁降级为兜底回复，观感是突然失忆。这是本刀最大的实现风险，处置见决策 5。选 (a) 能避开这个风险，但避开的方式是让护栏在最需要它的场景失效，等于用正确性换观感。

### 决策 5：时间归属误伤怎么应对

1. **面临的选择**：(a) 沿用 C3a 阈值不动，以联调实测为准；(b) 为回看单列一个更宽的阈值；(c) 回看路径关掉时间归属检查。
2. **选了哪个 + 为什么**：**(a)**。回看是这层护栏最该生效的场景——(c) 等于在最需要的地方把它关掉，(b) 会造出两个阈值、两种行为，而且在阈值本身都没校准的情况下就分叉，分叉依据不存在。本刀的正确定位是：**它是时间归属护栏的第一次真实压力测试**，实测数据比提前调参更有价值。
3. **放弃的代价**：接受实现期与联调初期可能出现较多误伤。缓解不是靠调参而是靠失败方向的选择——误伤的后果是一句兜底回复，而放宽的后果是把三个月前的心情冒充成此刻的心情。若联调实测误伤率确实高，**作为实测校准单独请示用户**，不在实现期自行调松（这与 C4 把 `min-coverage` 从 0.60 实测下调到 0.35 的做法一致：调整必须有实测依据）。

### 决策 6：回看是否复用既有会话端点

1. **面临的选择**：(a) 复用 `POST /api/agent/sessions`，请求体加 `purpose`；(b) 新增 `POST /api/agent/review-sessions` 一套端点。
2. **选了哪个 + 为什么**：**(a)**。会话的读取、追加消息、结束这三个端点在两种模式下的语义完全一致（同样按 sessionId 定位、同样的归属校验、同样的失败重试语义）。若开会话另起一套，紧接着就要回答「`getSession` / `sendMessage` / `finish` 要不要也复制一套」，而复制它们没有任何收益。`purpose` 缺省为 `WRITING_GUIDANCE`，既有前端调用无需改动。
3. **放弃的代价**：`POST /api/agent/sessions` 的请求体多一个可选字段，端点语义从「开写作引导会话」变成「开会话」。这是契约上的轻微泛化，需要在 delta 中明确；相比多三个近乎重复的端点，这个代价更小。

### 决策 7：为什么回看完全不给工具（out_of_scope 边界）

1. **面临的选择**：(a) 完全无工具；(b) 给一个「把这次的感想追加到回应」之类的写工具；(c) 沿用 C2 白名单（三个草稿工具，实际会因非 DRAFT 而全部执行失败）。
2. **选了哪个 + 为什么**：**(a)**（用户 Q6 定稿）。回看对象是已解锁记录，封存后 `location` / `attachments` / `cover` 不可变，正文也不应被回看对话追加——没有任何一个合法的写操作可做。关键是这一点必须**在代码层硬保证**：`buildToolContext` 当前只按「有无 recordId」判断是否下发 tools，而回看会话恰好绑定一条记录，所以「无工具」**不会自动成立**，必须按 purpose 显式短路；模型仍返回 tool_calls 时 fail-closed。
3. **放弃的代价**：(b) 会把「解锁后能改什么」这个已经定稿的产品边界重新打开，属于范围外。(c) 是最坏的——白名单挂着但每次执行都失败，用户会看到确认条然后收到失败提示，这正是 `AGENTS.md`「不得 mock success 冒充真实成功」反面的另一种形态：让用户确认一个注定失败的操作。

### 决策 8：为什么回看不产出可回填素材

1. **面临的选择**：(a) 不产出素材；(b) 产出素材，允许追加到记录正文；(c) 产出素材，但只能写进「后来其实」字段。
2. **选了哪个 + 为什么**：**(a)**。已解锁记录的正文属于「那时的自己」，往里追加此刻的整理会破坏这条记录的时间完整性——用户几个月后再看，无法分辨哪句是当时写的、哪句是回看时补的。实现上要注意 `sendMessage` 中 `targetStage == CLOSING` 会触发 `generateMaterial`，回看路径必须短路这一步（这也是决策 2 不复用 `CLOSING` 常量的原因之一）。
3. **放弃的代价**：(c) 看似合理——「后来其实」本来就是给解锁后写的。但它是既有 M4 能力、有自己的提交次数限制（`realityLaterSubmitCount` 上限 2），让 Agent 产出内容去填它会与既有约束纠缠，且用户尚未要求。留给未来独立 change。

### 决策 9：`selectActiveByUserAndRecord` 是否加 purpose 谓词

1. **面临的选择**：(a) 加谓词；(b) 不加，依赖「同一条记录不可能同时是 DRAFT 和 UNLOCKED」这个事实。
2. **选了哪个 + 为什么**：**(a)**。(b) 在当前实现下确实不会出错，但它让契约依赖一个巧合——一旦将来出现「解锁后允许再编辑」之类的变化，两种会话就会互相串，而这种 bug 的表现是「用户点回看却恢复了三个月前那次写作对话」，极难排查。加一个谓词的成本远低于此。
3. **放弃的代价**：查询多一个条件、既有调用点要传入 purpose。改动面很小，且编译期会强制所有调用点显式表态。

### 决策 10：为什么本刀不动 R2（引导与素材质量）

1. **面临的选择**：(a) 顺手优化——回看的开场话术本来就要新写，不如把引导话术一起改；(b) 严格不动，回看 prompt 是**新增**的角色设定。
2. **选了哪个 + 为什么**：**(b)**。用户已明确 R2 延后到 C1–C5 全部完工后统一优化，C3 两刀均不动。技术上也有理由：回看引入了新的 prompt 与 MEMORY 层高频复述，合并联调时观察到的任何语气变化都需要能归因；同时改写作引导话术会让两个变量纠缠在一起。
3. **放弃的代价**：写作引导的开场生硬问题继续存在一段时间。这是用户已知并同意的延后项。

### 决策 11：既有断言 `shouldNotCreateAnyReviewChatSession` 怎么处理

1. **面临的选择**：(a) 删除该测试；(b) 改为等价的正向断言；(c) 保留并给它加例外条件。
2. **选了哪个 + 为什么**：**(b)**。这条断言在 C3a 的语义是「本刀不实现回看」，属于**范围守护**。本刀实现回看后，该守护的原意失效，但它守护的另一半仍然有效——**写作引导会话不应产生 `REVIEW_CHAT` 用途**。改成这个正向断言既保住了有效部分，也不留下一条永远为真的空测试。按 `AGENTS.md`，修改既有断言须在 AGENT_LOG 显式披露。
3. **放弃的代价**：(a) 会让「写作引导误标 purpose」这个真实风险失去覆盖。(c) 加例外条件会让测试意图变模糊，读者无法一眼看出它在守护什么。
