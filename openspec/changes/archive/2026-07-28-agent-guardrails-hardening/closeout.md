## 1. 交付了什么

把「不改写用户原文」从 prompt 里的一句自觉条款，变成后端的**确定性拦截**。

| 能力 | 落点 |
|---|---|
| 忠实度双指标判定 | `agent/guardrail/AgentFaithfulnessChecker` + `AgentCoverageProfile` + `AgentSourceCorpus` + `AgentTextNormalizer` |
| 工具正文参数闸 | `AgentToolValidator`（与白名单 / 类型 / 边界同层，无绕过重载）→ 既有 `REJECTED_BY_GUARD` 通道 |
| 素材路径闸 | `AgentChatServiceImpl.generateMaterial` → 不忠实即 `materialDraft=null`（复用「可选产物」语义，前端零改动） |
| `askText` 伪引用 + 诊断 / 代决检查 | `AgentContentChecker`（引号片段用专用严判据） |
| 回复后置检查与降级 | `AgentContentChecker` → `AgentGuardrailDowngrade`（本地兜底常量，痕迹标 `fallback=local`） |
| 护栏规则单一声明源 | `AgentGuardrailRules`（prompt 文案 + 检查规则 + 正向行为清单） |
| 边界用例回归集 | `AgentGuardrailBoundaryCaseTest`（四类场景）+ R1 回归 + `AgentMaterialGuardrailTest` |

范围守护：未做 Memory（C3）、未做查询端点（C5）、**未调引导 prompt 与素材合成策略**（R2 延后）、白名单未扩大、未新增表、未新增依赖、前端零改动。

## 2. 核心问题的答案

**「怎么机械地判定忠实」** → 双指标：整体覆盖率 + **最长连续未覆盖片段**，基于字符级 n-gram，确定性、零外调、可单测。

为什么必须两个指标，实测给了比规划更强的证据：

| 样本 | coverage | maxUncoveredRun |
|---|---|---|
| R1 增写 | 0.449 | **38** |
| 合法整理（去口头语） | **0.500** | 6 |

合法整理的覆盖率**竟高于** R1，只差 5 个百分点——覆盖率单用几乎无区分度；而 maxUncoveredRun 差 6 倍以上。**未覆盖片段的分布形态而非总量，才是增写的特征。** 覆盖率因此退化为兜底辅判据。

配套边界：`askText` 只做宽判定（它天然是 Agent 自己的话），诊断 / 代决规则**只在新增区段匹配**（用户自述病症词被复述不误伤，否则 Agent 会被逼成「用户一提病名就换话题」）。

## 3. 规划被实测推翻的部分

**`min-coverage` 0.60 → 0.35**。规划阶段的推断值会把合法整理判死（实测仅 0.500）。这是规划保守推断与实测标定的差距，已在 design §3.3 留表记录，未悄悄改数。

**实现期补记决策 13**：11 字的伪造引用「我已经彻底放弃找工作了」正好低于短文本跳过阈值，两个判据都不触发就漏放了。根因是通用判据的宽容度是为「整理」留的，而引用没有整理余地——引号声称的是逐字原话。故引号片段单设 `QUOTE_MIN_COVERAGE=0.80` 且不跳过短文本。

## 5. 闸门 3 的诚实结论

**误伤方向已验证，拦截方向未活体验证。**

真实 DeepSeek 四次调用中：provider 可达；对话回复未触发诊断 / 代决检查；素材在正常输入下 coverage=**1.000**（与用户原话逐字等长 31 字），在**稀疏输入**（只说「有点累」「说不上来」）下 len=7、maxRun=3。全部判忠实，且离阈值有明显余量。

也就是说：**本轮没有复现 R1 的增写**。模型在素材不足时选择了「少说」而非「替用户补话」。因此闸门对真实发生的增写能否拦下，目前只有本地真实样本回归（用 C2 记录的原文构造）作为证据。不能据此认为 prompt 层已经够了——R1 恰恰证明 prompt 会被违反，这正是要有后置闸的理由。

**SKIPPED**：微信真机手验（T-47）与 C2 遗留的 T-40~T-42（T-48）——用户决定本轮优先快速完成阶段迭代，一并延后。MySQL 未启动（T-44），因本轮探针不写库。
