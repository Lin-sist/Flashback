## 2. 痕迹挂载方式（架构）

### 2.1 一个 per-turn 收集器，一个落库出口

```text
sendMessage 进入
   │
   ├─ 创建 TurnTrace 收集器（含 traceId、sessionId、turnNo、mode）
   │
   ├─ 阶段判定        → trace.thought(stageDecision.reason(), fromStage, toStage)
   ├─ 记忆检索        → trace.memory(enabled, candidateCount, injectedCount, totalChars)
   ├─ prompt 组装     → trace.prompt(messageCount, promptVersion, policyVersion)
   ├─ provider 调用   → trace.provider(model, durationMs, outcome, causeType)
   ├─ tool_calls 处置 → trace.tools(returnedCount, proposedCount, rejectedReasons, failClosed)
   ├─ 护栏各层        → trace.guardrail(layer, verdict)   // 可多次
   ├─ 降级            → trace.downgrade(path, violation)
   │
   └─ finally：traceSink.persist(trace)   ← 唯一出口，fail-open
```

**关键点：`persist` 放在 `finally` 语义的位置。** provider 失败、护栏降级、fail-closed 丢弃全都是**早退路径**——C3b 的教训是早退路径最容易被漏掉。把落库放在唯一出口，早退也会带着已收集到的部分落库，而不是什么都没有。

`persist` 自身包 try-catch 且只记 warn：**痕迹写不下去不能让用户这一轮对话挂掉**（沿用 C3a 记忆检索 fail-open 的既有做法）。

### 2.2 表结构方向（N1 定 a 时）

新表 `agent_turn_trace`，一轮一行。列分三类：

- **关联**：`id` / `trace_id` / `session_id` / `user_id` / `record_id` / `turn_no` / `attempt_no` / `purpose` / `stage`
- **版本**：`model` / `prompt_version` / `policy_version`
- **结果与指标**：`outcome` / `provider_duration_ms` / `cause_type` / `downgrade_path` / `violation` / `steps_json`（结构化步骤明细）/ `created_at`

`steps_json` 只装结构化值（枚举短标识、计数、长度、耗时、哈希前缀）。索引：`(session_id, turn_no)` 与 `(user_id, id)`。外键随 session / user 级联删除。

`attempt_no` 是为了让「同轮重试」可辨识（验收 4）——`(session_id, turn_no)` 在重试时会重复，不能靠它区分。

### 2.3 隐私边界（本刀最硬的一条）

痕迹允许的值只有三类：**结构化枚举短标识、数值、长度或哈希前缀**。

具体禁止清单：日记原文、对话原文、记忆片段内容、候选文本、未覆盖片段内容、prompt 全文、provider 原始响应体。

实现上不靠自觉：`TurnTrace` 的每个收集方法**只接受基础类型与既有枚举**，不接受任意 `String` 内容参数——想传原文进去在类型层就做不到。唯一的 `String` 类型入口是枚举的 `reason()` 短标识与 `AgentToolArgsDigest` 风格的摘要。

## 3. 决策记录

### 决策 1：痕迹存哪里（N1，偏离已冻结蓝图缓解措施）

1. **面临的选择**：(a) 新建 MySQL 表；(b) 结构化 JSON 日志文件——**这是蓝图 v1.1 §4 C5 风险栏明写的缓解措施**（「MVP 可用结构化 JSON 日志文件，不需要专用存储」）；(c) 扩 `agent_tool_call` 的列复用既有表。
2. **选了哪个 + 为什么**：**推荐 (a)，但因偏离已冻结蓝图，须用户裁决。** (c) 先被事实排除：`agent_tool_call` 只在有工具提议时才有行，而回复路径、素材路径、thought 侧全都没有行可挂，回看模式更是完全无工具——复用它等于只能观测到工具那一小段。(a) 与 (b) 的分野落在蓝图**自己的验收项**上：同一张卡片要求「提供开发者可查询的接口或日志解析工具」，而本地没有任何日志聚合（无 ELK/Loki，无 logback 配置），JSON 文件要按 session 查询就得自己写一个解析工具。更决定性的是 C6：蓝图 v1.2 草案要求 C5 为 C6 预留 `trace_id` / `prompt_version` / `policy_version` / `model`，C6 要拿它们做变更前后的回归对比——落在表里是一条 SQL，落在文件里是一个解析器加一套对比逻辑。
3. **放弃的代价**：选 (b) 的代价不是「省了一张表」，而是「把可查询的成本转移到一个还没写的解析工具上」，总工作量更大，且新增 logback 配置会触碰 `AGENTS.md`「不改 monitoring」的边缘。选 (a) 的代价是实打实的：多一张表、多一次 DDL（含 DDL 的 change 有明确流程教训，须列为实现期第一步）、每轮多一次 insert。蓝图那条缓解写在 C5 还很远的时候，当时尚不知道 C6 会要求字段级关联——这是本刀提出偏离的全部依据。

### 决策 2：记录粒度是每轮一条还是每步一行（N2）

1. **面临的选择**：(a) 每轮一条聚合记录，步骤明细放结构化 JSON 单列；(b) 每个步骤一行事件记录；(c) 两级结构（轮次表 + 事件表）。
2. **选了哪个 + 为什么**：**(a)**，附硬约束：埋点必须收敛到一个 per-turn 收集器 + 单一落库出口。理由是埋点分散会重演项目已经吃过教训的问题——C4 决策 5 花力气把分散在三处的护栏规则收敛到一个声明源，就是因为分散必然漂移。(b) 意味着 7~9 个 insert 散落在 `AgentChatServiceImpl` / `AgentToolCoordinator` / 三个 checker 里，而 provider 失败、护栏降级、fail-closed 全是**早退路径**，散落的埋点在早退时最容易被跳过——那正是最需要痕迹的时刻。
3. **放弃的代价**：(a) 的 `steps_json` 是半结构化的，按步骤类型做聚合查询不如 (b) 直接。但 C5 的查询场景是「给我这个 session 的轨迹」，不是「统计所有会话的护栏命中分布」——后者是 C6 的事，届时若确有需要可从 `steps_json` 里抽字段成列，成本低于现在就上两张表。(c) 同时承担 (b) 的分散风险与多一张表的成本，收益要等到 C6 才可能兑现。

### 决策 3：采样策略（N3，轻微偏离蓝图缓解措施）

1. **面临的选择**：(a) 默认全量，只提供总开关；(b) 默认全量 + 可配采样率（蓝图缓解措施提到「可配置采样率」）；(c) 默认按比例采样。
2. **选了哪个 + 为什么**：**推荐 (a)**。采样的失效方式非常具体：排查时最想看的那一轮，恰好可能没被采到——这不是理论担忧，C3b 的排查就依赖于「那一次到底发生了什么」。当前是单人本地开发 + 单机 MySQL，每轮一行的写入量距离构成问题还很远。为一个不存在的容量问题引入一个真实的排查盲区，不划算。
3. **放弃的代价**：将来若真有量，需要补采样能力——但那时补是有依据的，现在做是没依据的。这同样是对蓝图缓解措施的偏离（蓝图写了「可配置采样率」），故一并请示而非自行决定。

### 决策 4：「可查询」以什么形式暴露（N4）

1. **面临的选择**：(a) 只落库，提供只读查询 SQL 脚本 + mapper 查询方法 + 集成测试演示按 session 取链路；(b) `/admin/agent/traces` 只读端点，复用既有 `/admin/**` 鉴权；(c) 产品 API 下 `/api/agent/sessions/{id}/trace` 限本人访问。
2. **选了哪个 + 为什么**：**(a)**。(c) 直接违反 C5 非目标「不面向终端用户展示（不破坏朋友的交互感）」——即便加 debug 开关，也是在产品 API 上开了一个内部数据的口子。(b) 看起来最顺理成章，`/admin/**` 的鉴权链路确实已完整可用，但规划期核实到一件决定性的事：**`AuthRole.ADMIN` 全仓没有任何签发路径**，`UserServiceImpl.buildLoginResponse` 固定签 `USER`，因此该端点在真实环境**不可达**。要让它可达就得改认证签发逻辑——把认证风险塞进一个可观测 change，性价比极差，且触碰 `AGENTS.md` admin portal 边界。
3. **放弃的代价**：(a) 对蓝图验收项「查询接口或日志解析工具」是弱化解释——落在「或」的后半句。缓解是集成测试会实证「按 session 取到完整链路」，能力本身在，只是没有 HTTP 封装。若用户坚持要端点，次优是 (b) 的窄版本：只做只读端点、**不改任何签发逻辑**，并把「当前只能由集成测试访问」如实写进 spec 与 AGENT_LOG——不假装它可用，这一点比端点本身重要。

### 决策 5：是否把 V4/V5 的既有埋点缺口纳入本刀（N5）

1. **面临的选择**：(a) 纳入 C5；(b) 不纳入，另开 Type B 修。
2. **选了哪个 + 为什么**：**(a)**。V4 的内容是「`AgentGuardrailDowngrade.trace` 形参已含 sessionId/turnNo，但两个调用点全传 null」——即降级痕迹**关联不到会话**。这正是 C5 要解决的问题本身，把它推给另一个 change 等于把 C5 做一半，然后在 C5 的轨迹里留一段关联不上的空白。改动只是把已经在作用域里的变量传进去，风险极低。
3. **放弃的代价**：C5 的 diff 里多了两处与「新增轨迹」无直接关系的改动。缓解是在 AGENT_LOG 中单列说明这两处属既有缺陷补齐——按 `AGENTS.md`，顺手改动必须披露，而不是混在主改动里。

### 决策 6：版本字段怎么产生（N6）

1. **面临的选择**：(a) 手工维护版本常量，改 prompt 或规则文案时人工 bump；(b) 由 prompt 模板与规则文案的**内容哈希**自动派生短版本；(c) 本刀不做，留给 C6。
2. **选了哪个 + 为什么**：**(b)**。(a) 的失效方式是这类设计的经典结局——改了文案忘了 bump，于是 C6 拿到「版本号没变但行为已变」的数据。这比没有版本更糟：没有版本时你知道自己不知道，脏版本会让你以为自己知道。(b) 把版本与内容强绑定，改文案自动变化，且验证方式很直接——测试断言「修改文案后版本值变化」。
3. **放弃的代价**：哈希派生的版本不可读（`p:3f9a1c` 而非 `v2`），无法从版本号看出演进顺序。这个代价可以接受：C6 需要的是「能否判断两批数据是否同一版本」，不是「版本的先后」。(c) 会让 C5 交付一个缺了 C6 依赖字段的轨迹，违背蓝图对 C5 的预留要求，等于把问题原样推后。

### 决策 7：轨迹写入失败怎么处置

1. **面临的选择**：(a) fail-open——只记 warn，用户这一轮照常完成；(b) fail-closed——写不下痕迹就让这一轮失败；(c) 事务内写入，与业务数据同生共死。
2. **选了哪个 + 为什么**：**(a)**。方向选择的依据是失败成本对比：痕迹缺一条的代价是「这一轮不好排查」，而对话失败一轮的代价是**用户真实体验受损**。可观测是辅助设施，让辅助设施有能力搞挂主流程是本末倒置。(c) 尤其要避免——`sendMessage` 是 `@Transactional`，若痕迹写入进同一事务且失败，会把用户消息与 Agent 回复一起回滚掉，那正是 C1 花力气保证的「用户输入不丢」的反面。
3. **放弃的代价**：痕迹可能有缺失，理论上存在「最想看的那一轮恰好没记下」的情况。这与决策 3 反对采样是同一个担忧，但两者性质不同：采样是**主动**制造盲区，写入失败是异常路径下的被动缺失，且有 warn 日志兜底说明「这里本该有一条痕迹」。

### 决策 8：为什么本刀不解析 provider 的 token 用量（out_of_scope 边界）

1. **面临的选择**：(a) 顺带解析 `usage`，把 token 数记进轨迹；(b) 不解析，只在轨迹里留字段位置；(c) 完全不考虑。
2. **选了哪个 + 为什么**：**(b)**。token 用量对 C6 的成本回归确实有价值，但它需要动 `AgentModelClient` 的响应解析——那是 C5「只挂痕迹、不改行为」这条自我约束的第一个破口。一旦开始改 provider 响应解析，就要考虑 provider 不返回 `usage` 时怎么办、mock provider 要不要伪造，问题会连锁展开。(b) 留好字段位置，等 C6 真正需要成本数据时一并做，那时它是 C6 的正当范围。
3. **放弃的代价**：C6 若要做成本回归，得先补这一小块解析。代价可控，且届时它的需求形状会比现在猜的更清楚（比如是否需要区分 prompt/completion、是否需要缓存命中标记）。(c) 连字段都不留则会让 C6 面临改表，成本更高。

### 决策 9：为什么 C5 完全不做前端（out_of_scope 边界）

1. **面临的选择**：(a) 前端零改动；(b) 加一个开发者可见的调试面板（仅 dev 环境）；(c) 在既有对话浮层里加一个隐藏的 trace 入口。
2. **选了哪个 + 为什么**：**(a)**。蓝图 C5 非目标第一条就是「不面向终端用户展示（不破坏朋友的交互感）」。(c) 最危险——隐藏入口迟早会被触发，而且它把内部判定过程放到了用户能看到的容器里，与 C4 已接受的条款「用户 SHALL NOT 被告知护栏内部判定过程」直接冲突。(b) 即便限 dev 环境，也要在小程序里维护一套只在开发时存在的页面，属于为一次性排查造长期负担。
3. **放弃的代价**：排查时要去数据库或跑测试，不能在手机上直接看。这个代价与 C5 的定位一致——它是工程向能力，服务的是开发者的排查效率，不是产品体验。而且真机排查场景下，问题往往是「用户报了一个 sessionId」，拿着它去查库比在手机上翻面板更实际。

### 决策 10：为什么本刀不动 R2 与 R9

1. **面临的选择**：(a) 顺手优化——C5 要读遍整条链路，正好看清引导话术与检索的问题；(b) 严格不动。
2. **选了哪个 + 为什么**：**(b)**。用户已明确 R2 延后到 C1–C5 全部完工后统一处理，R9 留独立 change。技术上也有理由，且这个理由对 C5 尤其成立：**C5 的价值是提供观测基线**。如果在建立基线的同一刀里改了被观测对象，就得不到一个干净的「改动前」参照——C6 的回归对比会从第一天起就少了基准。
3. **放弃的代价**：引导话术的生硬问题继续存在。这是用户已知并同意的延后项，且 C5 完成后再优化，反而第一次有了「优化前后可对比」的条件——这本身是把 R2 放在 C5 之后的额外好处。

### 决策 11：轨迹的保留与清理（N7）

1. **面临的选择**：(a) 外键级联删除 + 可配保留天数 + 手动清理 SQL 脚本；(b) 引入定时任务自动清理；(c) 不做清理。
2. **选了哪个 + 为什么**：**(a)**。(b) 要引入调度机制（`@Scheduled` 或外部 cron），触碰 `AGENTS.md`「不改 deployment / monitoring」，而且自动删数据这件事在没有备份策略的本地环境里风险不对称——删错了没法恢复。(a) 把策略讲清楚、把工具给到手，执行时机交给人判断，符合「高风险操作要人确认」的一般原则。
3. **放弃的代价**：清理要人记得执行。缓解是级联删除已经覆盖了主要来源（用户或会话被删时轨迹自动走），保留期清理只针对长期堆积。(c) 在单机 MySQL 上迟早变成问题，且到那时表已经很大，清理本身会变成一次风险操作。
