# M3 Demo Core Flow Hardening

## Background

Flashback V2.0 is a WeChat Mini Program demo for presentation and review. M1 established the user-side visual foundation, and M2 stabilized the backend core around record lifecycle, privacy, list/timeline behavior, minimal AI fallback, and a subscription-message foundation.

M2 has been archived to `openspec/changes/archive/2026-06-07-m2-backend-optimization/`. Its backend-core requirements have been promoted to `openspec/specs/backend-core/spec.md` and remain accepted baseline constraints for M3.

The current project is not ready to be treated as a production release. The next useful step is to harden the demo into a complete user-side loop that can be tested with real identity and reminder behavior while preserving the quiet, private, gentle product intention.

The user has confirmed the following M3 decisions:

- M3 is demo hardening, not production launch.
- Account/password login stays available.
- Real WeChat login is required.
- Real unlock reminders are required, but WeChat subscription template IDs are not available yet and may be represented by configuration placeholders.
- AI should only provide gentle prompts and content organization.
- "你当时以为" should be organized by AI.
- "后来其实" may only be filled after unlock.
- "后来其实" may be submitted at most 2 times after unlock.
- Life nodes use fixed enum values first, with "其他" allowing a user custom label.
- Stage summary is generated by user manual action.
- Stage summary is generated on demand and is not persisted in M3.
- Admin portal is out of scope.
- Frontend priority is complete flow, not major visual polishing.
- The demo database may be rebuilt instead of migrated.

## Problem

The existing frontend and backend can support many parts of the V2.0 loop, but the demo is not yet a complete real-flow experience.

Important gaps for M3:

1. WeChat Mini Program login is not yet a real primary user flow.
2. Unlock reminders have backend foundation but do not yet provide a real subscription-message delivery path.
3. The product-specific reflection model is not structured enough:
   - "你当时以为"
   - "后来其实"
   - life node category
   - stage summary
4. The frontend can display the core pages, but the flow still needs better state alignment and backend-backed behavior.
5. OpenSpec needs a dedicated M3 fact source so implementation agents do not expand into admin, production launch, complex AI, or broad frontend redesign.

## Goals

M3 SHALL make the demo core flow real and verifiable:

1. Keep account/password login as a supported development and demo fallback.
2. Add real WeChat login for Mini Program users.
3. Support record creation with structured reflection fields.
4. Use user-triggered AI to organize "你当时以为" without replacing user original content.
5. Allow "后来其实" only after a record is unlocked, with at most 2 submissions.
6. Support life node records through fixed enum values plus a custom label for "其他".
7. Support real unlock reminder delivery flow through WeChat subscription messages, with configuration-placeholder behavior when template IDs are missing.
8. Keep reminder send idempotent and non-blocking for record unlock.
9. Add user-manual, on-demand stage summary generation without persistence.
10. Complete the user-side frontend flow without major visual reconstruction.
11. Permit demo database rebuilds where schema changes are needed.

## Non-Goals

M3 MUST NOT implement:

- admin portal
- production release hardening
- production deployment
- monitoring, alerting, or incident response
- SMS reminders
- production notification center
- admin template management or campaign delivery
- complex retry orchestration
- complex AI growth analysis
- social feed or sharing features
- real MAP / IMAGE / VOICE capability
- H5/Web user-side acceptance target
- broad frontend visual redesign
- broad backend rewrite
- package or lockfile changes unless explicitly required and justified

## Scope

### P0: M3 Fact Source and Guardrails

This OpenSpec change is the active fact source for M3 implementation.

Agents working on M3 MUST read:

- `AGENTS.md`
- `.ai/ACTIVE_TASK.md`
- `openspec/project.md`
- `openspec/specs/backend-core/spec.md`
- `openspec/changes/m3-demo-core-flow-hardening/proposal.md`
- `openspec/changes/m3-demo-core-flow-hardening/design.md`
- `openspec/changes/m3-demo-core-flow-hardening/tasks.md`
- relevant M3 spec deltas
- only directly required frontend/backend files

Agents MUST NOT implement uncertain backend API contracts until the user confirms the open contract decisions.

### P1: Authentication Flow Hardening

M3 includes:

- account/password login remains available
- real WeChat code login
- OpenID-based user lookup or user creation
- JWT reuse after successful WeChat login
- clear frontend login choice or fallback behavior

### P1: Record Reflection Model

M3 includes structured support for:

- AI-organized "你当时以为"
- user-filled "后来其实" after unlock
- life node enum
- custom life node label when enum is "其他"

The original user content MUST remain preserved.

### P1: Unlock Reminder Delivery

M3 includes real WeChat subscription-message delivery flow for record unlock reminders.

Because template IDs are not currently available, M3 MUST support explicit configuration-placeholder behavior:

- missing template ID does not block record seal or unlock
- missing template ID is recorded as a known send-unavailable state
- real send path is implemented when required configuration exists
- successful sends are idempotent
- failed sends are non-blocking

### P2: Frontend Core Flow Completion

M3 frontend work focuses on flow completion:

- login page supports account/password and WeChat login
- record editor supports reflection and life node inputs
- seal flow can request subscription authorization
- time review displays "你当时以为" and accepts "后来其实" only after unlock
- stage summary can be manually generated
- visible naming uses "我的记录", "时光轴", and "时间回看"

M3 SHOULD avoid major visual polish unless needed to make the flow understandable.

### P2: Stage Summary

M3 includes a user-manual stage summary feature.

The summary may use lightweight statistics and AI organization. It MUST remain a supporting reflection feature, not a complex analytics dashboard.

### P3: Demo Database Rebuild

M3 may update schema files and test schema directly. Demo database rebuild is allowed.

M3 does not need to create a full migration framework unless a later change explicitly requires it.

## Acceptance Criteria

M3 is accepted when:

1. This OpenSpec change clearly constrains M3 implementation.
2. Account/password login still works.
3. Real WeChat login works through Mini Program code login when configuration is available.
4. Missing WeChat configuration fails with explicit demo-safe behavior.
5. Users can create, save, seal, and later review records through backend-backed APIs.
6. AI can organize "你当时以为" without replacing original content.
7. "后来其实" can only be created or updated after unlock and cannot exceed 2 submissions.
8. Life node records support fixed enum values and custom label for "其他".
9. Unlock reminders have real subscription-message send path and non-blocking placeholder behavior when template IDs are absent.
10. Reminder send success is idempotent.
11. Stage summary is generated by user manual action, on demand, and not persisted in M3.
12. Frontend user flow is complete enough for demo acceptance.
13. Admin, production launch, complex AI, SMS, notification center, and broad redesign remain out of scope.
14. Real reminder delivery is manually verified after WeChat template IDs are configured.
15. Automated or manual verification evidence is recorded for the full demo loop in `.ai/AGENT_LOG.md`.

## Recommended Implementation Order

1. Establish M3 facts and read only required files.
2. Confirm backend API contracts with the user.
3. Update backend data model and contracts.
4. Implement WeChat login.
5. Implement reflection fields and AI organization boundary.
6. Implement life node enum and custom label behavior.
7. Implement reminder authorization, send path, and placeholder behavior.
8. Implement "后来其实" after-unlock write behavior.
9. Implement user-manual stage summary.
10. Connect frontend flow in a later integration phase.
11. Run focused backend tests, frontend type-check/build where applicable, and manual Mini Program flow verification.
