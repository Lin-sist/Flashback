# Agent Guardrails Hardening（C4）· Design

> Change ID：`agent-guardrails-hardening`
> 阶段：**规划闸（闸门 1）—— Q1–Q7 待用户确认** —— 本文不授权写业务代码
> 配套：`proposal.md`（范围与验收）、`tasks.md`（实施切片）、`specs/**`（契约 delta）
> 核心命题：把「不改写用户原文」从 prompt 自觉变成**后端确定性判定**

---

## 1. 架构总览

C4 在 `agent` 包内新增一个**检查层**，插在「模型产出」与「产出落地」之间。不重构 C1/C2 已有的编排结构。

```text
┌───────────────────────── 模型产出（C2 已有路径，不改协议） ─────────────────────────┐
│ AgentModelClient.completeWithTools → message.content（reply）+ message.tool_calls   │
│ AgentModelClient.complete         → material（素材路径，仍走 json_object）          │
└──────────────────────────────────────┬─────────────────────────────────────────────┘
                                       ▼
   ┌──────────── 新增：护栏检查层（com.flashback.agent.guardrail） ─────────────────┐
   │ AgentGuardrailRules        护栏规则唯一声明源（prompt 文案 + 检查规则 + 正向行为）│
   │ AgentSourceCorpus          来源集合：本会话用户原话的归一化索引（只读，不落库）   │
   │ AgentFaithfulnessChecker   忠实度判定：双指标 n-gram 覆盖比对 → 判定 + 结构化指标 │
   │ AgentContentChecker        诊断 / 代决措辞检查（只作用于「新增区段」）            │
   │ AgentGuardrailVerdict      判定结果：PASS / VIOLATION(type, reason, metrics)      │
   │ AgentGuardrailDowngrade    降级处置：拒绝提议 / 丢弃素材 / 兜底回复替换           │
   └──────────────────────────────────────┬─────────────────────────────────────────┘
                                          ▼
   ┌──────────── 既有落地路径（复用现成拒绝通道，不新建旁路） ─────────────────────┐
   │ AgentToolValidator   → 新增忠实度拒绝原因常量（G19）                           │
   │ AgentToolCoordinator → 复用 persistGuardRejected(...) 落 REJECTED_BY_GUARD（G18）│
   │ AgentChatServiceImpl → 回复兜底替换、素材丢弃；不改阶段推进与轮次语义           │
   │ AgentGuardrailPolicy → 保留长度硬裁剪；prompt 文案改为委托 AgentGuardrailRules  │
   └────────────────────────────────────────────────────────────────────────────────┘

   持久化：不新增表。工具路径复用 agent_tool_call.failure_type（Q6=b）
```

### 关键不变量

1. **检查在落地之前**。忠实度不通过的 `text` 永远不会成为待确认提议，用户看不到那个确认条——不是「先落库再标记」。
2. **fail-closed**。检查逻辑本身异常时按违规处理（拒绝 / 丢弃），绝不因检查失败而放行未检文本。
3. **多层叠加，不替换**。prompt 护栏（C1）、白名单（C2）、二段式确认（C2）、长度硬裁剪（C1）全部保留原效力；C4 是在其上加一层，不是取代其中任何一层。
4. **越界不毁掉整轮对话**。工具提议被拒 → 本轮 `reply` 照常返回（沿用 C2 数据流 2.1 要点一）。用户感知是「Agent 这次没提议」，不是「Agent 崩了」。
5. **来源集合只限当前会话**。忠实度比对的语料是本会话 `agent_message` 中 `role=USER` 的消息，**不做跨记录检索**——这是 C3 的边界，C4 不越。
6. **痕迹只存结构化指标**。覆盖率、未覆盖片段长度、判定类型可落；候选文本与用户原话**不落**审计表与日志。

## 2. 数据流

### 2.1 工具提议路径（核心，R1 的发生地）

```text
completeWithTools 返回 tool_calls
  → AgentToolCoordinator.handleProposals(...)
      → parseArguments → AgentToolValidator.validate(...)
          ├─ 白名单 / 类型 / 长度 / 边界（C2 既有，不动）
          └─ 【C4 新增】忠实度闸
                需要来源集合 → AgentSourceCorpus.of(本会话 USER 消息)
                AgentFaithfulnessChecker.check(text, corpus)
                  ├─ PASS      → 继续 C2 既有流程，落 PROPOSED
                  └─ VIOLATION → 返回 rejected(REASON_UNFAITHFUL_ARGS)
                                 → persistGuardRejected(...) 落 REJECTED_BY_GUARD
                                 → 本轮 reply 正常返回，无确认条
```

**为什么忠实度闸放在 `AgentToolValidator` 而不是更靠后的执行层**：C2 已经把「提议合法性」的全部判断收敛在这一个校验点上（`AgentToolValidator` 的类注释明确写着「白名单的最终强制点始终在后端」）。忠实度是提议合法性的一个新维度，放在同一处才能保证「不存在绕过校验的提议路径」。放到执行层则太晚——提议已经作为确认条呈现给用户了，用户会看到一条不该存在的建议。

**参数注入**：`AgentToolValidator.validate(...)` 当前签名是 `(wireName, rawArgs, hasDraft)`，没有会话上下文。忠实度需要来源集合，所以要扩签名（增加来源语料参数）。这是内部组件，非对外契约，改动面限于 `AgentToolCoordinator` 与其单测。

### 2.2 素材路径（Q2 若纳入）

```text
generateMaterial(history)
  → complete(buildMaterialMessages) → extractText(raw, "material")
  → 【C4 新增】AgentFaithfulnessChecker.check(material, corpus)
       ├─ PASS      → 作为 materialDraft 返回
       └─ VIOLATION → 丢弃素材（materialDraft = null）+ 记结构化日志
                      会话仍正常 ENDED，用户看不到回填入口
```

素材为可选产物，`AgentChatServiceImpl.generateMaterial` 的既有注释已声明「素材整理失败不影响会话结束：素材为可选产物，缺失时前端不展示回填入口」。C4 复用这条既有语义——不忠实的素材等同于「没生成出来」，前端无需任何改动。

### 2.3 回复路径

```text
reply（message.content 或 askText 兜底）
  → normalizeReplyShape（C2 格式兜底，不动）
  → 【C4 新增】AgentContentChecker.check(reply, corpus)
       ├─ PASS      → enforceReplyLength（C1，不动）→ 返回
       └─ VIOLATION → 替换为安全兜底回复 → enforceReplyLength → 返回 + 记结构化痕迹
```

回复**不进忠实度闸**——Agent 提问本来就是它自己的话，用「必须源自用户原话」判定会把一切提问判死（proposal §3.3）。回复受诊断 / 代决检查约束。

### 2.4 `askText` 的特殊处理

`askText` 既是提议话术（Agent 自己的话，如「要不要放进正文？」），又是唯一显示在确认条上的文本（G13/G15）。因此对它用**较宽的判定**：不做覆盖率比对，只做两件事——

- 诊断 / 代决措辞检查（同 §2.3）；
- **伪引用检查**：`askText` 中若出现引号包裹的片段，该片段必须在来源集合中有覆盖。理由：R1 的 `askText` 自称「我帮你把这两句整理了一下」，这类表述本身不违规，但一旦它引号引用了用户「说过的话」而用户没说过，就是在确认条上直接展示虚构内容。

## 3. 忠实度判定机制（本 change 的核心）

### 3.1 来源集合的构造

```text
AgentSourceCorpus.of(List<AgentMessage> history)
  取 role == USER 的全部消息（不设滑动窗口——会话上限 8 轮，全量可控）
  归一化：去空白、统一全半角、去标点、大小写折叠
  产出：归一化后的字符序列集合 + 其全部长度为 N 的 n-gram 集合
```

**为什么全量而非滑动窗口**：`contextMessageWindow=12` 是给 prompt 用的成本约束。忠实度判定在后端本地跑，零 token 成本，而用户在第 2 轮说过的话在第 7 轮被整理进正文是完全正常的。用窗口会造出「说过但被判虚构」的误伤。

**为什么去标点**：模型整理时几乎必然调整标点（口语「嗯就是那种」→「那种」）。保留标点会让覆盖率虚低。代价是无法区分「你想做后端。」与「你想做后端？」——但语气变化不是 R1 要防的问题。

### 3.2 双指标判定（Q1 方向 A）

```text
check(T, corpus):
  T' = 归一化(T)
  逐位标记 T' 中每个字符是否被 corpus 的 n-gram 覆盖
  指标 1：coverage      = 被覆盖字符数 / T'.length
  指标 2：maxUncoveredRun = 最长连续未覆盖字符数

  FAITHFUL  ⟺ coverage ≥ minCoverage  AND  maxUncoveredRun ≤ maxUncoveredRun阈值
```

**为什么必须两个指标，单靠覆盖率不够**——这是本机制设计的关键点，也是验收标准 4 存在的原因：

R1 的实测形态是「两句真话 + 一句约 45 字虚构」。用户原话约 30 字，虚构约 45 字，合成后的 `text` 假设约 90 字。即便虚构部分完全不覆盖，整体覆盖率仍有约 50%。而把 `minCoverage` 定到 50% 以上会大面积误伤——正常整理会引入连接词、删减重复，覆盖率本就不可能接近 100%。

**最长连续未覆盖片段**才是能区分两种情况的指标：

| 情形 | coverage | maxUncoveredRun |
|---|---|---|
| 正常整理（顺语序、删口头语、加连接词） | 中高 | **小**——未覆盖处零散分布在接缝上，每处几个字 |
| R1 型增写（插入整句虚构） | 可能仍中等 | **大**——一整段连续几十字都无来源 |

也就是说：**未覆盖片段的「分布形态」而非「总量」，才是增写的特征。** 这是把判定针对 R1 实际形态设计、而不是套用通用文本相似度的直接结果。

### 3.3 阈值初值（Q4，实现期用真实样本校准）

| 配置项（`app.agent` 下） | 初值 | 依据 |
|---|---|---|
| `guardrail.faithfulness-ngram-size` | 4 | 中文 4-gram 足以避免「单字碰巧命中」的假覆盖，又不过分严格 |
| `guardrail.min-coverage` | 0.60 | 留出整理引入连接词与删减的空间；不承担拦 R1 的主要职责 |
| `guardrail.max-uncovered-run` | 12 | 主判据。R1 虚构句约 45 字远超；正常接缝插入通常在 10 字以内 |
| `guardrail.faithfulness-enabled` | true | 总开关；关闭时退回 C2 行为并记结构化日志（不静默） |
| `guardrail.min-checked-length` | 12 | 短文本（如「好」「嗯」）不做覆盖率判定，避免小样本抖动 |

初值是**保守推断而非实测标定**，实现期必须用 R1 真实样本 + 若干正常整理样本回归校准，校准结果写入 AGENT_LOG。**不得把初值当作已验证阈值。**

### 3.4 诊断 / 代决检查（Q5）

规则形态：关键词 / 短语规则表，收敛进 `AgentGuardrailRules` 单一声明源。

```text
AgentContentChecker.check(T, corpus):
  分区：把 T 切成「有来源区段」与「新增区段」（复用 §3.2 的覆盖标记）
  只在【新增区段】上匹配诊断词 / 代决措辞
```

**为什么必须只查新增区段**：用户自己说「我可能有点焦虑症」，Agent 共情复述时带上这个词是**恰当**行为——蓝图 §6.4 要求的正是「共情回应」。若在全文匹配诊断词，这类正常回应会被误判，Agent 会被逼成「用户提到病名就闭嘴」，正好落入蓝图 C4 风险栏「过度限制导致 Agent 无话可说」。

两类规则：

- **诊断类**：病症名 + 判定式表述（「你这是……症」「典型的……表现」「建议你去看……」）。命中 → 回复替换为安全兜底。
- **代决类**：谎报已执行不可逆操作的表述（「我已经帮你封存了」「已经删掉了」「已经解锁」）。命中 → 回复替换为安全兜底。这一类补的是 C2 的盲区：白名单保证 Agent **做不到** seal，但拦不住它**说自己做了**。

**相称性检查建议不纳入 C4**（Q5）：C1 的 `maxReplyChars=120` 硬上限已经覆盖「用户写两行、Agent 回三百字」的主要风险，而「回复不得长于用户表达」的动态相称会在用户只答「嗯」时把 Agent 逼到一个字，反而破坏气质。

### 3.5 与 R2 的关系（说明，不实施）

用户要求 R2（引导突兀 / 素材生硬）延后到全部阶段完工后统一优化，同时要求若 C4 的忠实度定义天然回答了「顺一遍语序算不算改写」，在 design 中说明关系。

**回答：算忠实，不算改写。** §3.2 的双指标在机制上就是这么落的——顺语序、删口头语、加连接词，产生的是接缝处若干个短未覆盖片段（每处远小于 12 字），`maxUncoveredRun` 不触发；整体覆盖率也维持在阈值之上。所以「整理」被明确允许，「增写」被明确拒绝。**忠实度的分界线是「有没有新增语义内容」，不是「有没有动过文字」。**

这条边界对 R2 的意义是划清了未来优化的活动空间：R2 想让素材更通顺，可以调语序、可以删冗余、可以改连接方式——这些都在忠实度闸放行的范围内。R2 唯一不能走的路是「让 Agent 补写用户没说的话来让段落更完整」，而那本来就是 R1 要禁止的。

**C4 不做的事**：不调 `stageGoal` 的引导话术、不改 `buildMaterialMessages` 的合成策略、不动素材拼接逻辑。C4 只在这些路径的**出口**加一道拦截。R2 的质量优化仍待用户在全部阶段完工后统一安排。

## 4. 护栏规则声明源收敛（Goals 5）

现状是三处分散（G10）：

| 现状位置 | 内容 |
|---|---|
| `AgentGuardrailPolicy.MINIMUM_GUARDRAILS` | 5 条最小护栏文案 |
| `AgentPromptBuilder.buildToolSupplement()` | 工具气质约束（提议而非代决、不得改写原文） |
| `AgentPromptBuilder.buildMaterialMessages()` | 素材约束（只用用户说过的内容、不加分析） |

C4 后：`AgentGuardrailRules` 成为唯一声明源，同时承载 prompt 文案与检查规则，两者从同一份声明派生。这样「prompt 里说不许诊断」与「后置检查拦诊断」不会漂移——这是 C2 决策 1 里「白名单是 tools schema 的唯一事实源」同一思路的复用。

`AgentGuardrailPolicy` 保留（`enforceReplyLength` 是 C1 已接受的护栏，且被多处调用），其 `guardrailClause()` 改为委托 `AgentGuardrailRules`。**不改 `enforceReplyLength` 的行为**。

规则声明同时包含**正向行为**（蓝图 §6.4：温和引导、共情回应、尊重沉默、行动建议），避免护栏只有负面清单。

## 5. 验证策略

| 层 | 手段 | 外调 |

| 忠实度判定核心 | JUnit 5 + AssertJ 纯单测（沿用 `agent/*Test` 风格）。含 **R1 真实样本回归**与整理不误伤用例 | 0 |
| **双指标必要性** | 显式测试：R1 样本在「仅覆盖率」判据下**通过**、在「加最长未覆盖片段」判据下**被拦**。这条测试是验收标准 4 的证据 | 0 |
| 归一化 | 单测：全半角、标点、空白、大小写的等价性 | 0 |

| 代决检查 | 单测：「我已经帮你封存了」被拦 | 0 |
| fail-closed | 单测：检查内部异常时返回违规而非放行 | 0 |
| 工具路径接入 | Mockito 单测 + H2 集成测试：UNFAITHFUL → `REJECTED_BY_GUARD`、无 `pendingToolCall`、本轮 reply 正常 | 0 |

| 隐私 | 单测 + 集成断言：痕迹与日志只含结构化指标，无候选文本与用户原话 | 0 |
| 回归 | `mvn -B test` **339 项基线** | 0 |
| 前端 | `type-check` + `build:mp-weixin`（若 Q6 选可见才有改动） | 0 |
| 真实联调 | 闸门 3 授权后：复现 R1 场景验证被拦；观察阈值是否误伤真实整理；阈值校准 | ≤ 30 |
| 微信手验 | 真机：忠实度拒绝后对话继续、兜底回复观感；**补 C2 遗留 T-40~T-42**（R3） | 含在上一行预算内 |

**回归底线**：339 项必须全绿，且**不得为 C4 便利修改任何 C1/C2 既有断言**。若某条既有断言与 C4 行为冲突，说明存在契约冲突而非测试问题，须停下请示。

**阈值校准的处置顺序**：若闸门 3 观察到误伤真实整理，顺序是「放宽 `max-uncovered-run`」→「降低 `min-coverage`」→「缩小 `min-checked-length` 适用范围」；**任何情况下不关闭忠实度闸来换取通过率**——那等于回到 R1 的状态。

## 6. 隐私与安全

- 忠实度判定的输入包含用户日记语境文本，但**全程在内存中**：来源语料不落库、不落日志、不外发。判定结束即释放。
- 痕迹只允许结构化指标：`coverage`（数值）、`maxUncoveredRun`（数值）、判定类型、失败原因常量。**不落**候选文本、不落用户原话、不落未覆盖片段内容。
- 工具路径复用 `agent_tool_call.failure_type`（Q6=b），沿用 C2 决策 6 的「只存摘要」边界，不新增列、不新增表。
- 应用日志沿用 C1/C2 已接受的结构化日志契约：sessionId / turnNo / 检查类型 / 判定结果 / 指标值。
- **安全兜底回复是本地常量**，不是 provider 产物。它在痕迹中可与真实回复区分（验收标准 12）——这是对 `AGENTS.md`「真实路径不得 mock success 冒充真实成功」的对齐：兜底不伪装成模型正常输出。
- 无新增 secret、无新增凭证字段、无新增外部服务调用。忠实度判定零外调是其设计前提之一。
- **prompt injection 的防线分层**：结构层沿用 C2（白名单 + 二段式），内容层由 C4 忠实度闸补上——即便模型被日记正文里的诱导指令带偏产出改写文本，改写内容在用户原话中无来源，会被拦下。C4 建立 injection 边界用例集，但**不声称**能识别注入意图本身。

## 7. 决策记录

### 决策 1：忠实度怎么机械判定——机械覆盖率闸 / 消息 id 引用 / LLM-as-judge

1. **面临的选择**：(a) 保留自由文本参数，后端用字符级 n-gram 做「整体覆盖率 + 最长连续未覆盖片段」双指标比对；(b) 把 `append_record_content.text` 改成 `sourceMessageIds`，正文由后端按 id 从 `agent_message` 取原文拼接，模型只做选择不产出文本；(c) 再调一次模型做 LLM-as-judge，让它判断候选文本是否忠实于用户原话。
2. **选了哪个 + 为什么**：**(a) 为主，(b) 记为后续可选加强，明确否决 (c)**——待用户在规划闸确认（Q1）。选 (a) 的决定性理由是它是三者中**唯一同时满足**四个硬条件的：确定性（同输入必同输出，可写回归测试）、零外调（不增成本与失败面）、可单测（纯函数）、不改已接受契约（C2 的工具参数契约保持原样）。而蓝图给 C4 的硬要求里就有「建立边界用例测试集，可持续回归验证护栏有效性」——这条要求本身就排除了任何不确定性的判定机制。更关键的是，(a) 的双指标形态不是套用现成的文本相似度算法，而是**针对 R1 的实际形态**设计的：R1 是「真话夹一句虚构」，整体覆盖率仍有约一半，只有「最长连续未覆盖片段」这个指标能把「零散接缝」与「整段增写」区分开（§3.2 有推算）。否决 (c) 的理由是根本性的：护栏若不可复现，就无法回归，也无法在换 model 后判断护栏是否还在；而且用同类系统守护同类系统，防御深度可疑——被诱导产出虚构的那个模型，同样可能被诱导判定虚构为忠实。
3. **放弃的代价**：选 (a) 的代价有三条，都必须承认。其一，**理论上可被绕过**——若模型大量复用用户原话的词汇来编造（每个 4-gram 都碰巧命中），双指标都可能通过。这是已接受的残余风险，须写进 closeout，不声称杜绝。其二，**阈值需要校准**，初值是保守推断而非实测标定，误伤与漏放的平衡要靠闸门 3 的真实样本调。其三，**同义替换会被误伤**——模型把「想做后端」改成「希望从事服务端开发」会判不忠实，虽然本产品其实并不想要这种重写。选 (b) 的防御强度确实高于 (a)（表示层不可能违反 vs 事后检验），但代价是彻底放弃「整理」：口语、重复、语序混乱会被逐字搬进正文，**素材会比现在更生硬**——而素材生硬正是 R2 里用户已经抱怨过的问题，把 (b) 设为默认等于让一个已知痛点变严重；此外还要 MODIFIED C2 刚接受的工具参数契约。选 (c) 的代价是每次提议多一次真实外调（成本、延迟、又一个失败面），判定不可复现导致边界用例集失去意义，且它把护栏的可靠性押在了「同一个刚刚犯错的模型这次会答对」上。

### 决策 2：忠实度闸插在哪一层——校验点 / 执行层 / 前端展示层

1. **面临的选择**：(a) 插进 `AgentToolValidator`，与白名单、类型、边界校验同层，不通过则提议不落库；(b) 插进 `AgentToolExecutor`，提议照常呈现，用户点确认后执行前才检查；(c) 不在后端拦，改为前端在确认条上完整展示 `text` 全文，让用户自己判断。
2. **选了哪个 + 为什么**：(a)。C2 已经把「提议是否合法」的全部判断收敛在 `AgentToolValidator` 这一个点上，其类注释明确写着「白名单的最终强制点始终在后端」。忠实度是提议合法性的一个新维度，放在同一处才能保证系统里不存在「绕过忠实度检查的提议路径」——这与 C2 决策 12 拒绝「前端回传参数」是同一条理由：**校验点必须唯一**。(b) 太晚：提议已经作为确认条呈现给用户了，用户会看到一条本不该存在的建议，即便执行时被拦，Agent 也已经在界面上说过「我帮你整理了一下」这句不该说的话。
3. **放弃的代价**：(a) 需要给 `AgentToolValidator.validate(...)` 扩签名注入来源语料——它当前不持有会话上下文。这是内部组件改动，影响面限于 `AgentToolCoordinator` 与其单测，可接受。选 (b) 的代价是虚构内容已经对用户可见，护栏退化为「执行失败提示」，用户体验上还多出一次莫名其妙的失败。选 (c) 的代价最大且方向错误：它把安全责任推给用户，要求用户逐字校对 Agent 产出的每段文字——这与产品「安静、克制」的气质相悖（确认条会变成一堵文字墙），而且用户本来就是因为信任才点「好」的，把审校负担还给他等于承认护栏做不到。

### 决策 3：违规被检出后怎么处置——一律拒绝 / 截断放行 / 分路径处置

1. **面临的选择**：(a) 任何不忠实产出一律整条拒绝；(b) 截断到忠实部分后放行剩余内容；(c) 按路径分别处置——工具提议拒绝、素材丢弃、回复替换兜底。
2. **选了哪个 + 为什么**：(c)（Q3 待确认）。三条路径的失败成本不同，用同一种处置反而不合理。工具提议的失败成本最低——拒绝后用户只是「少看到一个确认条」，对话完全不受影响（复用 C2 已验证的 `persistGuardRejected` 通道，本轮 reply 照常返回）。素材是可选产物，`generateMaterial` 的既有语义就是「失败即为 null，前端不展示回填入口」，丢弃能无缝复用这条已存在的降级路径，零前端改动。回复不能拒绝也不能丢——用户提交了一轮消息，必须得到回应，否则对话看起来像挂了，所以只能替换为安全兜底回复。**失败方向是刻意选的**：宁可少一个确认条 / 少一段素材，也不放行一句用户没说过的话进他的日记。
3. **放弃的代价**：选 (c) 的代价是三条路径各有一套处置逻辑与测试，实现面比统一处置大。选 (a) 的代价是回复路径无法「拒绝」——用户会得到一次空回应，比兜底回复更糟。选 (b) 的代价最隐蔽也最危险：截断意味着后端**自己动手改**模型产出的文本，一是切出来的半句话语义可能扭曲甚至反转，二是这与「不改写」的立场自相矛盾——护栏为了守护原文完整性而去裁剪文本，逻辑上说不通。而且截断后的文本仍要再判一次，容易陷入循环。

### 决策 4：诊断检查为什么只查「新增区段」而不是全文

1. **面临的选择**：(a) 在候选文本全文匹配诊断词表；(b) 复用忠实度的覆盖标记，把文本切成「有来源区段」与「新增区段」，只在新增区段匹配。
2. **选了哪个 + 为什么**：(b)。用户自己说「我可能有点焦虑症」时，Agent 共情复述带上这个词是**恰当行为**——蓝图 §6.4 明确要求「共情回应」。若全文匹配，这类正常回应会被判违规，Agent 会被逼成「用户一提病名就换话题」，正好掉进蓝图 C4 风险栏点名的「过度限制导致 Agent 无话可说」。区分「谁说的」比区分「说了什么词」更接近真实的护栏意图：产品禁止的是**Agent 下诊断**，不是禁止病名这个字符串出现。附带好处是这个分区能力是忠实度覆盖标记的免费副产品，不需要第二套机制。
3. **放弃的代价**：(b) 依赖覆盖标记的准确性——若归一化或 n-gram 判定有偏差，分区也会偏，可能把 Agent 新增的表述误判为有来源而漏检。缓解是分区只用于**放宽**（避免误伤），漏检的兜底仍是 prompt 层的「不诊断」约束与人工手验。选 (a) 的代价是高频误伤共情回应，且误伤的都是产品最想要的那类回复，护栏会变成气质的敌人。

### 决策 5：护栏规则要不要从三处收敛到单一声明源

1. **面临的选择**：(a) 保持现状，prompt 文案留在 `AgentGuardrailPolicy` / `buildToolSupplement` / `buildMaterialMessages` 三处，C4 的检查规则另起一处；(b) 收敛到 `AgentGuardrailRules` 单一声明源，prompt 文案与检查规则从同一份声明派生。
2. **选了哪个 + 为什么**：(b)。蓝图 §4 C4 目标 4 明确要求「为护栏规则产出可维护的配置/文档，而非散落在 system prompt 中」。但更实质的理由是**防漂移**：如果 prompt 里写「不许诊断」而后置检查的词表是另一份独立清单，两者会随时间分叉——改了一处忘了另一处，就会出现「prompt 允许但检查拦」或「检查放过但 prompt 禁止」的自相矛盾状态，而这种矛盾极难在测试里发现。这与 C2 决策 1 让 tools schema 从白名单单一派生是同一个思路。
3. **放弃的代价**：(b) 要动 `AgentPromptBuilder` 与 `AgentGuardrailPolicy` 两个 C1/C2 已验收的类，有回归风险——缓解是只搬移文案来源、不改 `enforceReplyLength` 行为、不改 prompt 的实际文字内容，让既有 `AgentPromptBuilderTest` / `AgentGuardrailPolicyTest` 保持通过（若必须改断言则停下请示）。选 (a) 的代价是 C4 结束时护栏变成**四处**分散，比现状更糟，且违背蓝图对本 change 的明确要求。

### 决策 6：素材路径要不要纳入忠实度闸

1. **面临的选择**：(a) 只覆盖工具参数 `text`，因为 R1 是在那里被观测到的；(b) 同时覆盖素材草稿。
2. **选了哪个 + 为什么**：(b)（Q2 待确认）。素材与工具参数在**结构上完全同质**：都是模型产出的文本、都会在用户点一下之后进入 `record.content`、都只有 prompt 约束而无后置校验（G7/G8）。R1 先在工具路径被观测到纯属偶然——手验那次 Agent 选择了提议工具而非收束。只做工具路径等于修好一扇门却把旁边同样大的门留着开，而且 C4 的 closeout 会很难写：「已系统化护栏」但「素材可以随便增写」。
3. **放弃的代价**：(b) 让改动面从一个校验点扩到两个路径，且素材路径仍走 `complete()` + `response_format=json_object` 的旧协议（G7），需要在不同调用形状上接同一个检查器。缓解是检查器本身是纯函数、与调用协议无关，只是接入点多一处。选 (a) 的代价是留下一条已知的等价漏洞，等于把同一个问题分两次做——而 R2 的统一优化会大量触碰素材路径，届时缺口会被放大。

### 决策 7：为什么不在 C4 顺手优化引导 prompt 与素材合成（R2）

1. **面临的选择**：(a) 既然 C4 要动 prompt 声明源与素材路径，顺手把 R2 的引导突兀与素材生硬一起优化；(b) 严格守住「只拦不改」的边界，R2 留到全部阶段完工后统一优化。
2. **选了哪个 + 为什么**：(b)。首要理由是用户已明确要求 R2 延后，并判断它接近大模型微调范畴、需要在 C1–C5 全部完工后统一收集逐个优化——这是范围授权问题，不是技术判断问题。技术上也有独立理由：C4 的价值在于交付一道**可回归的确定性闸**，而 R2 的优化是**主观质量调优**，两者的验收方式完全不同（前者看测试红绿，后者看手验体感）。混在一个 change 里会让验收失焦——阈值误伤和引导话术不自然会互相掩盖，说不清是护栏太严还是 prompt 太差。
3. **放弃的代价**：C4 期间引导突兀与素材生硬**依然存在**，用户手验 C4 时仍会遇到 R2 的体感问题，需要事先知道这不是 C4 的验收范围。另一个代价是 §3.5 只做了「顺语序算忠实」的边界说明而没有实际改善素材质量，用户可能感觉 C4 «拦住了坏的但没让好的变好»——这是刻意的分工，护栏与质量本就该分开做。

### 决策 8：降级痕迹要不要对前端可见

1. **面临的选择**：(a) 只落后端痕迹与结构化日志，前端完全无感；(b) 向前端下发降级标识，界面上给用户一个提示（如「这次的建议没通过检查」）。
2. **选了哪个 + 为什么**：(a)（Q6 待确认）。产品气质是「共情型朋友」，而不是一个会自曝内部审查过程的系统。告诉用户「Agent 刚才想说的话被拦下了」既无行动价值（用户做不了什么），又破坏朋友感——它把对话变成了一个有监控指示灯的软件。工程侧的可见性需求是真实的，但它的正确归属是 C5 的决策链路可查询（开发者向，蓝图 D11 明确「工程向，不面向用户」），不是往用户界面塞状态。附带好处是前端零改动，C4 变成纯后端 change，回归面小。
3. **放弃的代价**：手验时开发者无法从界面上直接看出「这一轮发生了降级」，得去查日志或 `agent_tool_call.failure_type`。这在闸门 3 阈值校准阶段会略微降低效率——缓解是结构化日志已包含判定类型与指标值，足以定位。选 (b) 的代价是把护栏的存在感推给用户，且一旦阈值误伤，用户会频繁看到莫名的拦截提示，对产品气质的伤害大于工程便利的收益。

### 决策 9：为什么不引入第三方分词或相似度库

1. **面临的选择**：(a) 引入中文分词或文本相似度库（如 jieba 类、simhash 类实现），在词级别做覆盖比对；(b) 用 JDK 内可实现的字符级 n-gram。
2. **选了哪个 + 为什么**：(b)。`AGENTS.md` 约束「不改 package / lockfile，除非任务明确要求并说明原因」，而本 change 并不需要词级精度——**中文字符级 n-gram 对「整段增写」这种粗粒度差异已经足够敏感**（§3.2 的 maxUncoveredRun 判据只需要知道「连续多少字没来源」，不需要知道词边界）。引入分词还会带来新问题：分词器对口语、错别字、网络用语的切分不稳定，反而给判定引入不可控变量，而护栏最需要的性质恰恰是确定性。
3. **放弃的代价**：字符级判定在同义替换上比词级更钝（「后端」vs「服务端」完全不覆盖），可能误判合法的近义改写。但如决策 1 所述，本产品并不想要 Agent 做近义重写——用户原话的措辞本身就是要保留的东西（`AgentGuardrailPolicy` 的第 2 条护栏原文即「需要引用时原样引用」）。所以这个「代价」与产品意图方向一致，不构成实际损失。

### 决策 10：`propose_unlock_at` 保留还是移除（R5 收口）

1. **面临的选择**：(a) 保留在白名单中；(b) 借 C4 这个「代决检查」的主题一并从 registry 移除。
2. **选了哪个 + 为什么**：**建议 (a) 保留，但请用户在规划闸明确一次以关闭 R5**。理由与 C2 design §3.4 一致且未被新证据推翻：它写的是 `unlock_at` 这个**可逆的草稿字段**，记录仍是 DRAFT、仍可继续改、封存那一步仍需用户自己在编辑页确认。真正不可逆的操作（seal）依然不可由 Agent 触达。C2 闸门 3 的越界实证（R1）出在**内容忠实度**上，与 `propose_unlock_at` 的权限边界无关，不构成移除它的证据。
3. **放弃的代价**：保留意味着 R5 的「体感是否越界」判断继续挂在用户主观感受上，若后续手验中觉得别扭仍需再动一次 registry。移除的代价是失去一个已实现、已测试、且是三种参数形状之一（字段设置型）的工具——白名单会只剩两种形状，未来新增同类工具时少了参照，且属于在没有证据的情况下收缩已验收能力。
