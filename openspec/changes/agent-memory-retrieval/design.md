# Design：Agent Memory Retrieval（C3 前半刀）

> Change ID：`agent-memory-retrieval`
> 阶段：**规划闸（闸门 1）—— 待用户批准**
> 配套：`proposal.md`（Why / 现状 / 验收）、`tasks.md`（切片）、`specs/**`（delta）

---

## 1. 架构总览

本刀在既有 Agent Runtime 上增加**一条上下文来源**与**一层来源分层**，不改编排骨架。

```text
用户提交一轮消息
  │
  ▼
AgentChatServiceImpl.sendMessage
  │
  ├─(1) 读会话历史  agentMessageMapper.selectBySessionId
  │
  ├─(2) 【新增】MemoryPort.retrieve(userId, purpose, cue, limit)
  │        └─ MySqlMemoryRepository：标签 + 时间窗 + title/core_question/ai_summary/belief_then LIKE
  │           └─ 返回 List<MemoryFragment>{recordId, occurredAt, label, text}
  │
  ├─(3) 【新增】memorySupplement = AgentPromptBuilder.buildMemorySupplement(fragments)
  │        └─ 与 C2 的 toolSupplement 同形态：system 段追加位
  │
  ├─(4) 组装 prompt  buildConversationMessages(stage, history, draftExcerpt, toolSupplement, memorySupplement)
  │
  ├─(5) 【改】来源集合  AgentLayeredCorpus.of(history, injectedFragments, ngramSize)
  │        ├─ SESSION 层 ← 本会话 role=USER 全文（= 今天的 AgentSourceCorpus，语义不动）
  │        └─ MEMORY  层 ← 本轮**实际注入**的片段原文
  │
  ├─(6) provider 调用（既有）
  │
  └─(7) 护栏判定
         ├─ 素材 / 工具 text  → 只认 SESSION 层（决策 4）
         ├─ 回复 / askText    → 认两层 + 【新增】时间归属检查（决策 2）
         └─ 引号伪引用        → 认两层，沿用 QUOTE_MIN_COVERAGE=0.80
```

关键点：**(2)(3) 是纯增量，(5) 是包装式增量，(7) 是既有判定的分层化。** 没有任何一步要求改写 `AgentChatServiceImpl` 的既有编排顺序或 `AgentSourceCorpus` 的既有语义。

## 2. 数据流

### 2.1 检索（新增）

输入：`userId`、`purpose`、检索线索 `cue`、条数上限。

`cue` 的构成（本刀定为**最近若干条用户消息 + 当前草稿的标签**，不含 Agent 表达）：
- 标签维度：当前草稿已绑定的 `tag_id` 集合 → 命中 `record_tag` 中同标签的其他记录。
- 关键词维度：从最近用户消息里取词，对 `title` / `core_question` / `ai_summary` / `belief_then` 做 LIKE。
- 时间维度：`created_at` 落在配置的回看窗口内（默认 N 个月），排除当前会话绑定的记录本身。

输出：`MemoryFragment` 列表，每项含 `recordId`、`occurredAt`、时间标签文案（如「三月」）、片段文本（截断到单条上限）。

**不扫 `record.content`**（Q3 定稿 + N3=(a)）。**排除 SEALED 未解锁记录**（N2=(b)）。

### 2.2 注入（新增）

`buildMemorySupplement` 产出一段 system 追加文本，形如：

```text
你还记得的一些事（只用于理解他，不是正文素材）：
- [2026-03·记录12] <片段>
- [2026-05·记录27] <片段>
提到这些时必须说清是哪个时候的，不要让它听起来像他刚刚说的。
```

三条设计约束：
1. 时间锚点必须**在文本里可读**——它既是 prompt 指令的依据，也是时间归属检查的语义目标。
2. 明写「不是正文素材」——与决策 4 的后端硬拦形成 prompt + 代码双层。
3. 文案取自 `AgentGuardrailRules` 单一声明源（C4 决策 5 的既有约定），不在 `AgentPromptBuilder` 里内联新规则。

### 2.3 来源分层（改）

```text
AgentLayeredCorpus
  ├─ session(): AgentSourceCorpus   // 既有类，构造方式不变
  └─ memory():  AgentSourceCorpus   // 由 ofTexts(fragments) 构造
```

`AgentCoverageProfile` 增加按层计算能力，产出三类信息：
- `coverage(SESSION)` / `coverage(ANY)`；
- `maxUncoveredRun(ANY)`（= 今天的语义，两层都无来源的最长连续段）；
- **`memoryOnlyRuns()`**：仅被 MEMORY 覆盖、不被 SESSION 覆盖的连续片段及其长度 —— 时间归属检查的唯一输入。

### 2.4 判定（改 + 新增）

| 路径 | 认哪些层 | 新增判定 |
|---|---|---|
| 素材草稿 `materialDraft` | **仅 SESSION** | — |
| 工具参数 `text` | **仅 SESSION** | — |
| `askText` | SESSION + MEMORY | 时间归属 |
| 对话回复 `reply` | SESSION + MEMORY | 时间归属 |
| 引号片段 | SESSION + MEMORY | 沿用 0.80 严判 |

## 3. 关键不变量

1. **来源只含本轮实际注入的片段**：检索到但因条数上限被丢弃的片段，**不得**进入 MEMORY 层。实现上必须由「注入用的同一个列表」构造 corpus，不得各自取一次。
2. **正文只认本会话**：任何进入 `record.content` 的文本，其合法来源集合恒为 SESSION 层单层。这条不可配置。
3. **fail-closed 对护栏，fail-open 对能力**：检索失败 → 不注入、对话继续；判定失败 → 判违规。两者方向相反且不得互相污染。
4. **不放宽既有阈值**：`minCoverage=0.35`、`maxUncoveredRun=12`、`minCheckedLength=12`、`QUOTE_MIN_COVERAGE=0.80` 初值不动。
5. **用户隔离**：检索 SQL 恒带 `user_id` 谓词，无例外分支。
6. **memory 片段不落库、不入日志、不进审计**：与 C4 的来源集合同级别隐私约束。
7. **Agent 不得为「显得有记忆」而编造关联**：无命中即不注入，prompt 中不出现占位式的空 memory 段。

---

## 4. 验证策略

- **纯离线可测**：分层 corpus、按层覆盖、时间归属判定、注入文本组装 → 单元测试，零 provider。
- **Mock provider 集成测试**：检索命中 → 注入 → 判定放行 / 降级的端到端；跨用户隔离；SEALED 排除；检索异常时对话继续。
- **负例固定**：未注入的记录内容不构成合法来源（防不变量 1 退化）；memory 内容进正文素材被拒（防不变量 2 退化）。
- **基线保护**：既有 397 项不改断言；`AgentSourceCorpus` 现有测试全部保留（N1 选包装式的直接收益）。
- **闸门 3**：真实 provider 观察时间归属的自发率与误伤率；memory 是否被错误当素材。

## 5. 决策记录

### 决策 1：Memory 进来后，忠实度闸的合法来源怎么定

1. **面临的选择**：(a) 不扩来源，Agent 能读 memory 但不能复述；(b) 扩来源，含本轮实际注入的片段原文，片段带 `recordId` + 时间锚点，引用须时间归属；(c) 只把 `ai_summary` 摘要而非原文纳入来源。
2. **选了哪个 + 为什么**：**(b)**（用户 2026-07-29 定稿）。它是唯一能让蓝图 §6.4「记忆关联」那一行示例行为在代码上合法的选项，同时用「只含本轮实际注入」把来源面钉死在可控范围内——不是「用户这辈子说过就算」。时间锚点 + 时间归属要求把「把三个月前的话当成此刻说的」这一具体危害单独封住。
3. **放弃的代价**：选 (a) 会得到一个哑巴——检索成本照付，Agent 一提历史原话就被自家 `checkQuotes` 判伪引用，功能等于没做。选 (c) 泄露面更小，但 `ai_summary` 覆盖率未知（proposal M16），更要命的是它把 AI 的旧产出当成「用户来源」，等于让 Agent 的历史输出成为新一轮增写的合法依据 —— 这正是 `AgentSourceCorpus` 注释里明确警惕的自我失效路径。

### 决策 2：「引用须时间归属」怎么机械判定

1. **面临的选择**：(a) 只写进 prompt，靠模型自觉；(b) 后端确定性检查——仅 MEMORY 覆盖的连续片段若无时间归属表述则判违规；(c) 再调一次模型判断表述是否有时间归属。
2. **选了哪个 + 为什么**：**(b) + prompt 双层**。C4 已经用一次实证证明「只写进 prompt」的约束会被违反（R1 的「不改写用户原文」就是 prompt 里写着的），所以 (a) 不能单独成立。(b) 的可行性来自分层 corpus：「哪些片段只来自 memory」是可计算的，不是语义判断；判定输入是位图，输出确定、可单测、零外调，满足 C4 立下的护栏标准。
3. **放弃的代价**：选 (a) 则时间归属只是一句自觉条款，无法回归验证，换 model 后无从知道它还在不在。选 (c) 违反 C4 已否决的方向 C——每次判定多一次外调、结果不可复现、无法写边界用例集，且用同类系统守护同类系统。

### 决策 3：分层来源集合的实现形态

1. **面临的选择**：(a) 改 `AgentSourceCorpus` 内部为「层 → n-gram 集合」映射，对外补按层查询；(b) 新建 `AgentLayeredCorpus` 包装两个 `AgentSourceCorpus`；(c) 扁平集合里给每个 n-gram 打层标记。
2. **选了哪个 + 为什么**：**(b)**（推荐，待用户确认 N1）。既有 397 项测试里大量直接构造并断言 `AgentSourceCorpus` 的行为，(b) 让这些路径**完全不动**，新能力全在新类里，回归风险最低。多一个类的代价换基线安全，划算。
3. **放弃的代价**：选 (a) 会牵动既有类的构造与查询语义，改断言的概率高，而 `AGENTS.md` 要求改既有断言必须披露请示——把风险提前引入。选 (c) 更省内存，但同一个 n-gram 可能同时属于两层，标记语义会变成集合运算，代码复杂度不匹配收益；且 `containsNgram` 的现有语义会被迫改变。

### 决策 4：memory 片段能不能成为正文素材

1. **面临的选择**：(a) 能——memory 是用户自己写的，追加进正文合理；(b) 不能——正文只认本会话表达，memory 只是理解材料；(c) 能但需用户额外确认。
2. **选了哪个 + 为什么**：**(b)**。产品语义上，用户此刻在写「这一刻」，把三个月前的句子搬进今天的记录是替他改写自己的时间线，而不是帮他表达。工程上，允许 (a) 会让忠实度闸的防御面被 memory 撑开——检索命中越多，能「合法」写进正文的文本就越多，等于把 C4 好不容易钉住的正文入口重新放宽。所以不变量 2 定为「正文恒只认 SESSION 单层」且不可配置。
3. **放弃的代价**：选 (a) 会让「三个月前的话被追加进今天的日记」成为一条正常路径，而用户可能几个月后解锁才发现；选 (c) 看似安全，但 C4 的 R1 已经证明二段式确认在内容不透明时会反过来成为通行证（确认条只显示 `askText`），多一次确认买不到安全。

### 决策 5：检索用什么实现

1. **面临的选择**：(a) 标签 + 时间窗 + 结构化字段 LIKE，不加索引；(b) 给 `record.content` / `ai_summary` 加 ngram FULLTEXT 索引；(c) 外部搜索引擎 / 向量库。
2. **选了哪个 + 为什么**：**(a)**（用户 Q3 定稿）。个人级数据量下，`user_id` + 时间窗 + `status` 已能借既有复合索引把扫描面压到很小；不动 DDL 就不需要为高敏正文建索引，隐私面最小；也不碰 package / lockfile。
3. **放弃的代价**：选 (b) 要为最高敏字段建立可被检索的结构，且 MySQL 中文全文检索需 ngram parser 配置，属于为「相关性略好」承担持久的隐私与运维负担。选 (c) 直接违反蓝图 D7（不做第二套企业 RAG / 向量中台），且与 RAG 项目叙事重复。

### 决策 6：检索失败时倒向哪一边

1. **面临的选择**：(a) 全局 fail-open——检索失败则不注入，一切照旧；(b) 全局 fail-closed——检索失败则该轮对话失败；(c) 分方向：能力 fail-open，护栏 fail-closed。
2. **选了哪个 + 为什么**：**(c)**。Memory 是增强而非依赖，检索挂了让整轮对话失败违反 baseline 的「Agent 可用性 SHALL NOT 成为记录生命周期的依赖」精神，也让一个可选能力变成单点故障。但护栏方向必须相反：没注入 memory 就没有 MEMORY 层来源，此时判定应当**照旧严格**（等价于 C4 现状），绝不能因为「检索失败了所以宽容一点」而放行。
3. **放弃的代价**：选 (a) 一刀切会连带把护栏的失败也当作可放行；选 (b) 会让 LIKE 查询的一次超时毁掉用户正在进行的写作对话。

### 决策 7：memory 检索排除哪些记录状态

1. **面临的选择**：(a) 全部状态都可检索；(b) 排除 SEALED 未解锁；(c) 仅 UNLOCKED + DRAFT。
2. **选了哪个 + 为什么**：**(b)**（推荐，待确认 N2）。封存的产品语义是「把回答权交给时间」，用户自己都还没到能看的时刻，Agent 抢先复述内容等于替时间拆封 —— 这是气质问题，不是技术问题。DRAFT 是用户当下就能看到的内容，纳入无碍。
3. **放弃的代价**：选 (a) 会出现「Agent 说出用户自己现在看不到的句子」这种破坏封存体验的场景；选 (c) 把 DRAFT 也排掉过于保守，会丢掉最近期、最相关的素材。

### 决策 8：`agent_session.purpose` 列在哪一刀建

1. **面临的选择**：(a) 本刀建列（默认 `WRITING_GUIDANCE`），后一刀只加行为分支；(b) 留给后一刀一起做。
2. **选了哪个 + 为什么**：**(a)**（推荐，待确认 N4）。一次 DDL 胜过两次，且 `MemoryPort.retrieve` 的签名天然需要 `purpose` 维度（写作引导与回看对话的检索偏好不同）。本刀只建列 + 默认值，**不实现** `REVIEW_CHAT` 的任何行为。
3. **放弃的代价**：选 (b) 会让本刀的 `MemoryPort` 签名里带一个当时无处取值的参数，或者后一刀被迫改 Port 签名 —— 而 Port 的稳定性正是拆两刀时最该保护的东西。

### 决策 9：为什么不向前端下发「本轮用了 memory」

1. **面临的选择**：(a) 不下发；(b) 下发布尔标识；(c) 下发引用的 recordId 列表。
2. **选了哪个 + 为什么**：**(a)**（推荐，待确认 N5）。蓝图 §6.2 写的是「它记得你写过的东西……但不会拿这些来分析你」。把「我检索了你的历史」显式化，会把朋友变成一个展示检索日志的系统。开发者的调试诉求属 C5 可观测范围，不该借用户可见字段来满足。
3. **放弃的代价**：选 (b) 前端会长出一个需要文案与视觉表达的状态，且无法解释给用户听；选 (c) 更糟——等于在 UI 上暴露命中了哪几条记录，用户会立刻开始琢磨「它为什么翻出这条」，与「安静、克制」的产品气质正面冲突。

### 决策 10：为什么本刀不做回看对话（拆刀边界）

1. **面临的选择**：(a) 按蓝图原样一刀做完 C3 三个子能力；(b) 拆两刀，先 Memory；(c) 拆两刀，先回看会话。
2. **选了哪个 + 为什么**：**(b)**（用户 Q1 定稿）。两个子能力的改动面几乎不重叠——Memory 集中在上下文与 `guardrail` 包，回看集中在会话模型、状态机、已接受 spec 条款与新前端浮层；合并会产出一份过长且互相阻塞的 tasks。选先 Memory 的理由是依赖方向：回看对话的价值全在「Agent 记得你」，它必须消费 Memory 才成立。
3. **放弃的代价**：选 (a) 单刀体量过重，闸门 2 之后长时间没有可验收的中间态，一旦中途发现来源分层的设计问题，回看部分的工作会被一起返工。选 (c) 会先交付一个只能就当前这一条记录空聊的浮层，那是今天 `record-detail` 静态摘要的加长版，用户价值低且验收标准难写。

### 决策 11：为什么不提供「扫 content」的配置开关

1. **面临的选择**：(a) 完全不做；(b) 做一个默认 `false` 的开关；(c) 默认开启。
2. **选了哪个 + 为什么**：**(a)**（推荐，待确认 N3）。留一个默认关闭的开关，等于把「无索引全表扫最高敏字段」这条路径写进生产代码却不为它写测试、不为它评估性能与隐私。要做正文检索就该等一个独立 change 正经做（含索引方案与隐私评估）。
3. **放弃的代价**：选 (b) 的代价是代码里存在一条未验证路径，而 `AGENTS.md` 的能力五态明确禁止把 `unknown` 当 `confirmed`——一个没测过的开关正是这种东西。选 (c) 直接违反用户 Q3 定稿。

### 决策 12：为什么本刀不动引导话术与素材合成（R2 边界）

1. **面临的选择**：(a) 顺手优化——反正 Memory 会让引导更有料；(b) 严格不动，Memory 只作为新增上下文段存在。
2. **选了哪个 + 为什么**：**(b)**。用户已明确 R2 延后到 C1–C5 全部完工后统一优化，两刀均不动。技术上也有理由：Memory 注入本身就会改变模型的输出分布，如果同时改引导话术，闸门 3 观察到的任何变化都无法归因。
3. **放弃的代价**：选 (a) 会让「引导变自然了吗」与「memory 起作用了吗」两个问题的证据互相污染，且越出用户已划定的范围。

### 决策 13：为什么不引入 embedding / 向量相似度做相关性

1. **面临的选择**：(a) 关键词与标签匹配；(b) 引入本地 embedding 模型或第三方相似度库；(c) 调 provider 的 embedding 接口。
2. **选了哪个 + 为什么**：**(a)**。蓝图 D7 已把「简单检索」定为 C3 的边界，且 `AGENTS.md` 禁止改 package / lockfile。选 (c) 还会把用户日记原文送去做 embedding，扩大高敏数据外发面。
3. **放弃的代价**：相关性确实弱于向量检索，蓝图关键风险栏已接受这一点（「初期可接受；后续独立 change 升级检索能力」）。本刀在 closeout 中须诚实记录相关性的实际观感，不粉饰。

## 6. 隐私边界

| 数据 | 允许存在的位置 | 明确禁止 |
|---|---|---|
| memory 片段原文（= 其他记录的日记原文） | 内存中的 `MemoryFragment`、发往 provider 的 prompt、内存中的 MEMORY 层 corpus | `agent_message`、`agent_tool_call`、应用日志、护栏痕迹、任何 tracked file |
| 检索命中信息 | 结构化指标（命中条数、片段总长、时间跨度） | 命中的文本内容、`recordId` 以外的记录字段 |
| 时间归属判定痕迹 | 结构化指标（memory-only 片段数与长度、判定结论、违规类型） | 片段内容、用户原话 |
| 来源集合（两层） | 仅内存 | 落库 / 日志 / 外发 |

`recordId` 视为可记录的结构化标识（沿用 C2 审计对 `record_id` 的既有处理），但**不得**伴随内容一起出现。

## 7. 与 baseline spec 的关系

本刀须以 **MODIFIED** 修订 `agent-runtime` spec 中四条把跨记录检索划给「后续 change」的 scenario：
- C1「范围内的记忆能力」
- C2「范围内的记忆能力」
- C4「范围内的记忆能力」
- C4 忠实度条款下的「来源集合的边界」（现措辞：来源集合 SHALL NOT 包含跨记录的历史检索结果）

修订方式沿用 C4 的既有做法：保留原 scenario 作为该阶段的范围声明，并加一行指向本刀的新条款，**不删除历史**。第四条须实质改写来源边界，改为「SESSION 层 + 本轮实际注入的 MEMORY 层」的分层表述，并保留「正文只认 SESSION 层」这一更严的约束。

delta 落点：`agent-runtime`（主契约 + 四条 MODIFIED）、`backend-core`（MemoryPort、检索约束、配置项）、`v2-product-scope`（记忆气质与封存语义边界）。**`miniapp-core` 不动**（N5=(a) 前端零改动）。
