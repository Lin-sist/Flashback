## 1. 项目总览

### 一句话定位

一款帮助用户写下当下、封存记录、延迟解锁、并在解锁时获得 AI 回信的私密时间胶囊微信小程序。

### 2.3 记录状态机与 ai_summary / ai_prompt_result 存储格式

```
DRAFT ──seal()──► SEALED ──定时任务──► UNLOCKED
         ↑                              |
         |                              └─► 用户可写 reply / realityLater
         └── 仅 DRAFT 可编辑/删除/更新位置/附件/封面
```

**状态流转触发条件**（代码证据）：
- `DRAFT → SEALED`：`RecordServiceImpl.seal()` (L270-292)，要求 `content` 非空且 `unlockAt` 在当前时间之后
- `SEALED → UNLOCKED`：`RecordUnlockScheduler` 每分钟执行，调用 `RecordServiceImpl.runUnlockJob()` (L484-509)
- 乐观锁通过 `WHERE status='DRAFT'` / `WHERE status='SEALED'` 保证幂等

**`ai_summary` 字段**：纯文本字符串。`AiSummaryVO` 共有 6 个维度（`summary/confusion/emotion/coreQuestion/desiredOutcome/beliefThen`），**只有 `summary` 字段**被存入 `record.ai_summary`，其余 5 个维度**不持久化**到数据库，仅在 API 响应时返回。（代码证据：`RecordServiceImpl.create:143` — `record.setAiSummary(normalizeOptional(request.getAiSummary()))` 只接收前端传来的字符串）

**`ai_prompt_result` 字段**：JSON 数组字符串，例如 `["问题一","问题二","问题三"]`，反序列化使用 Jackson `TypeReference<List<String>>`。

**AI 总结的 6 个维度（`AiSummaryVO` VO 字段）**：
1. `summary` — 综合摘要（唯一持久化到数据库的维度）
2. `confusion` — 当前困惑点
3. `emotion` — 情绪状态
4. `coreQuestion` — 核心问题
5. `desiredOutcome` — 期望结果
6. `beliefThen` — 那时以为（"曾经的信念"）

> ⚠️ **重要发现**：除 `summary` 外，其余 5 个维度在封存后**不持久化**，无法被 RAG 检索利用。数据库的 `belief_then` 列是**用户手写或前端从 AI VO 中提取后主动传回服务端**的字段，与 `ai_summary` 中的 `beliefThen` 维度是独立存储的。

## 3. 核心业务流程（带时序）

### 3.1 记录完整生命周期

```
用户端                        后端                          外部服务
  |
  |── POST /api/records ──►  RecordController.create()
  |                          RecordServiceImpl.create()
  |                          · 校验 content 非空
  |                          · status=DRAFT, unlockAt=用户设置值
  |                          · ai_summary / ai_prompt_result 由前端传入存储
  |◄── RecordDetailVO ───────────────────────────────────────────────
  |
  |── POST /api/records/{id}/seal ──►  RecordServiceImpl.seal()
  |                                   · 校验 content 非空 & unlockAt > now
  |                                   · status: DRAFT → SEALED
  |◄── RecordDetailVO ──────────────────────────────────────────────
  |
  |   [等待 unlock_at 到期...]
  |
  |                    RecordUnlockScheduler.runUnlockJob()    (每分钟)
  |                    · selectExpiredSealedRecords(now, limit=100)
  |                    · unlockSealedById: status SEALED→UNLOCKED
  |                    · insertUnlockNoticeLog
  |                    · createUnlockReminderIfAbsent ──────►  微信订阅消息 API
  |
  |── GET /api/records/{id} ──►  RecordDetailVO (status=UNLOCKED)
  |
  |── POST /api/records/{id}/reply ──►  ReplyServiceImpl.create()
  |                                    · 校验 status=UNLOCKED
  |                                    · 校验唯一性（uk_reply_record_id）
  |◄── ReplyVO ─────────────────────────────────────────────────────
  |
  |── PUT /api/records/{id}/later-reflection ──►  最多提交 2 次
```

### 3.2 定时解锁任务详解

- **位置**：`RecordUnlockScheduler.java` (L23)
- **频率**：`@Scheduled(cron = "${app.record.unlock-job-cron:0 */1 * * * *}")` — **每分钟执行一次**（秒级 cron）
- **批量策略**：每次循环最多处理 100 条 (`UNLOCK_BATCH_SIZE=100`)，循环直到无待解锁记录
- **幂等性**：SQL `WHERE status='SEALED' AND unlock_at <= now` + `affectedRows=1` 判断，并发安全
- **微信推送**：解锁后调用 `createUnlockReminderIfAbsent` → 查 `record_reminder` 表 → 若有授权且未发送则 `sendUnlockReminder` → `WechatSubscribeMessageClient.sendUnlockReminder()`
- **推送失败处理**：`reminder_status` 更新为 `SEND_FAILED`，`last_error` 记录原因，不阻塞解锁主流程（`RecordServiceImpl:633` — `catch(Exception ex)` 静默处理）

### 3.3 鉴权体系

- **JWT 拦截器**：`JwtAuthenticationInterceptor` 注册在 `/api/**` 和 `/admin/**`，排除 `/api/auth/**`
- **白名单**：`/api/auth/register`、`/api/auth/login`、`/api/auth/wechat-login`
- **双通道**：
  - 账号密码：`UserServiceImpl.login()` → BCrypt 验证 → 签发 JWT
  - 微信：`UserServiceImpl.wechatLogin()` → `WechatSessionClient.exchangeCodeForSession(code)` → code2session → 查/建用户 → 签发 JWT
- **Token 结构**：HMAC-SHA256 签名，Claims 含 `userId` + `role`，过期时间 2 小时（可配置），**无刷新机制**
- **每次请求**：拦截器从 JWT 取 userId，再查一次 `user` 表确认账号状态（L78-86），保证账号禁用实时生效

- **输出**：`AiWritingPromptsVO { prompts: List<String>, source, status, message }`
- **Prompt 模板**（L303-315，Java text block 内联）：
  ```
  System: "你是《时光回序》的写作辅助，只帮助用户温和地整理当下，不做诊断或评价。"
  User:   "请为一条私密时间记录生成3个温和、克制、可继续书写的问题。
  ```

#### ② 记录总结（Summarize Record）

- **入口**：`POST /api/ai/summarize-record`

- **输出**：`AiSummaryVO { summary, confusion, emotion, coreQuestion, desiredOutcome, beliefThen, source, status }`（6 个维度）
- **Prompt 模板**（L318-331）：
  ```
  System: "你是《时光回序》的内容整理助手，表达安静、私密、克制。"
  User:   "请整理这条私密时间记录中"你当时以为"的相关内容。
           只输出JSON，格式为{summary, confusion, emotion, coreQuestion, desiredOutcome, beliefThen}。
           不要替换用户原文，不要做心理诊断。"
  ```
- **调用时机**：用户在编辑器内主动点击"整理记录"时调用
- **持久化**：前端从返回 VO 中提取 `summary`（→ `aiSummary`）、`beliefThen`（→ `beliefThen`）随记录保存请求传回后端

#### ③ 阶段总结（Stage Summary）

- **入口**：`POST /api/stage-summaries/generate`（用户主动触发）
- **输入**：无请求体（从 userId 查最近 20 条记录拼接 context）
- **输出**：`StageSummaryVO { summary, recordCount, unlockedCount, lifeNodeCount, source, status, generatedAt }`
- **Context 构建**（`StageSummaryServiceImpl` L83-101）：拼接记录的 `title/content/beliefThen/realityLater`，截断到 5000 字符
- **Prompt**：请求生成一段"温和、克制的阶段总结"，仅输出 `{"summary":"..."}`

### 4.5 若要新增"历史记录向量检索 + Agent 回信"的接入评估

**最合理的接入触发点**：`RecordServiceImpl.runUnlockJob()` (L484-509) — 解锁成功后，在 `insertUnlockNoticeLog` 之后新增 Agent 回信生成调用。记录已 UNLOCKED、内容已固定（封存后不可修改），符合"在解锁时生成有洞察力回信"的产品逻辑。

**需要新增的后端组件：**

| 组件 | 类型 | 说明 |
|------|------|------|
| `record_embedding` 表 | 新表 | 存储每条记录的向量索引（recordId, userId, embeddingVector, embeddedAt, status） |
| 向量数据库 | 外部依赖 | pgvector（MySQL 不支持向量，需引入 PostgreSQL/pgvector 或独立向量库） |
| `EmbeddingService` | 新 Service | 调用 Embedding API（DeepSeek/OpenAI text-embedding-3-small 等），生成并存储向量 |
| `RecordEmbeddingScheduler` | 新 Schedule | 批量为历史记录生成 Embedding（历史补档） |
| `MemoryRagService` | 新 Service | 给定当前解锁记录，检索 Top-K 相关历史记录 |
| `AgentReplyService` | 新 Service | RAG 结果 + 当前记录 + 历史召回 → 构建 prompt → 调用 LLM → 生成回信 |

## 8. 面向"个人记忆 RAG + Agent 回信"的可扩展性结论

### 8.1 改造评估矩阵

| 模块 | 操作 | 预估改造量 | 风险点 |
|------|------|------------|--------|
| `reply` 表 | `content` TEXT 化，新增 `reply_type=AI_AGENT_REPLY`，新增 `ai_context` JSON 列 | **小** | UNIQUE 约束不变，向后兼容 |
| `ReplyServiceImpl` | 放开 replyType 限制，新增后端创建 AI 回信的入口 | **小** | 需处理幂等（已有 reply 时不重复生成） |
| `AiService` / `AiServiceImpl` | 新增 `generateAgentReply(userId, record, relatedRecords)` 方法 | **小** | 可复用 `invokeChatCompletion()` 框架 |
| `AgentReplyService`（新） | RAG 检索 + LLM 调用 + 回信生成 | **中** | Prompt 设计、token 成本、超时处理 |
| `MemoryRagService`（新） | 向量检索 Top-K 相关记录 | **中** | 需要引入向量库依赖 |
| `EmbeddingService`（新） | 调用 Embedding API，存储向量 | **中** | Embedding API 选型、成本 |
| `record_embedding` 表（新） | 存储向量（JSON/BINARY 或外部向量库） | **中** | MySQL 8.4+ 才支持 VECTOR，需确认版本 |
| `RecordServiceImpl.runUnlockJob()` | 解锁后异步触发 Agent 回信生成 | **小** | 需异步（@Async 或消息队列），不阻塞主流程 |
| `pom.xml` | 引入 Embedding/向量库/Spring AI 依赖 | **小** | 依赖冲突评估 |
| 历史数据 Embedding 批处理 | 为存量记录生成 Embedding | **大** | API 成本、速率限制、幂等处理 |
| 前端 `record-detail` 展示 | 区分 AI 回信 vs 用户回信的展示样式 | **小** | 已有回信展示模块，仅需增加类型判断 |

### 8.2 已为这件事打好基础的部分

- ✅ **`invokeChatCompletion()` 封装完善**：OpenAI-compatible 协议、超时配置、JSON 强制输出，对 Agent 回信完全复用
- ✅ **Provider 三态设计**（MOCK/DEEPSEEK/OPENAI_COMPATIBLE）：可无缝切换 Embedding API 提供商
- ✅ **`reply` 表有 UNIQUE 约束**：天然保证每条记录只有一条 AI 回信，不会重复生成
- ✅ **解锁任务单一入口**：`runUnlockJob()` 是唯一触发点，接入 Agent 回信只需修改一处
- ✅ **`record` 表有 `content/beliefThen/realityLater`**：RAG 的原材料已存在，内容结构清晰
- ✅ **`user_id` 贯穿所有表**：用户隔离已完备，向量检索天然可按 `user_id` 过滤
- ✅ **AI fallback 机制**：已有三态（SUCCESS/FAILED/FALLBACK），Agent 回信可复用
- ✅ **前端回信展示模块已存在**：`record-detail/index.vue` 已有 `replyResult` 和 `showReplySheet` 逻辑

### 8.3 会成为阻碍的部分

- ❌ **MySQL 无向量原生支持**（当前 MySQL 版本未知，8.4+ 才有 VECTOR 类型，需确认）
- ❌ **`reply.content` 为 VARCHAR(500)**：Agent 生成的回信可能超过 500 字，必须 ALTER TABLE
- ❌ **`ReplyServiceImpl` 硬限 `replyType=SHORT_REPLY`**（L94-96）：需修改才能接受 AI 回信写入
- ❌ **无异步任务队列**：当前解锁是同步循环，AI 生成可能耗时 5-10 秒，需引入 `@Async` 或消息队列
- ❌ **无 Embedding 基础设施**：需从零引入，包括向量数据库选型、依赖管理、历史数据补档
- ❌ **Redis 引入但未使用**：可用于缓存 Embedding 或记忆检索结果，但当前未初始化
- ❌ **AiService 为同步阻塞调用**：Embedding + RAG + LLM 串行调用总超时可能超过 30 秒，需异步化
