# 时光回序 V2.0 优化实施文档（供 codex /goal 执行）

## 0. 全局约束（最高优先级，违反即视为失败）

1. **范围锁死**：本次任务**只做第 0 步与第 1 步**，禁止触碰回信链路、前端 UI、鉴权、
   定时解锁逻辑、七牛上传逻辑等任何范围外代码。遇到"顺便优化一下"的冲动，一律停手。
2. **真实优先**：只基于工作区真实代码改动，禁止脑补不存在的类/表/字段。动手前先用
   3~5 分钟扫描确认 `AiSummaryVO`、记录实体类、记录表的真实结构与字段名，以扫描到的
   真实名称为准（下文出现的类名/字段名若与真实代码不符，以真实代码为准并在 commit 里说明）。
3. **不破坏现状**：所有改动必须向后兼容，现有"草稿→封存→定时解锁回看"主流程必须始终可跑通。
4. **分阶段提交**：每完成一个阶段（Stage）立即 `git commit`，message 用**中文**，
   格式：`feat(memory): <阶段简述>` 或 `fix/refactor/chore` 前缀。禁止把两个阶段塞进一次提交。
5. **可回滚**：数据库变更必须走迁移脚本（新增字段/表用 ALTER/CREATE，禁止 DROP 旧字段、
   禁止改动旧字段类型）。回填脚本必须可重复执行（幂等），不得产生重复数据。
6. **完成即自检**：每个 Stage 结束后，自己跑一遍验收清单并在 commit 描述里勾选确认。

## 第 0 步：抢救被丢弃的 5 个情绪维度（地基，必须先做）

### 背景
当前 AI 总结产出 6 个维度（`summary / confusion / emotion / coreQuestion /
desiredOutcome / beliefThen`），但**只有 `summary` 被持久化**，其余 5 个在封存后丢弃。
这 5 个维度是后续个人记忆 RAG 与 Agent 回信的核心原料，必须先落库。

### Stage 0.1：数据模型扩展
- 新增持久化字段，承载 5 个维度。**二选一，按现有代码风格决定**：
  - 方案 A（推荐，查询简单）：在记录表上直接新增 5 列：
    `confusion / emotion / core_question / desired_outcome / belief_then`（均为 TEXT，可空）。
  - 方案 B（维度多变时更灵活）：新建 `memory_ai_dimension` 表，外键关联记录 id，
    `dimension_key` + `dimension_value`，一对多。
- 用迁移脚本（Flyway/项目现有迁移机制）实现，文件名带版本号与中文注释。
- **验收**：迁移可执行、可重跑不报错；新字段默认可空，不影响旧数据插入。
- 完成后 commit：`feat(memory): 新增5个AI情绪维度的持久化字段与迁移脚本`

### Stage 0.2：写入逻辑补全
- 定位调用 DeepSeek 生成 `AiSummaryVO` 的 Service，将 5 个维度与 `summary`
  一并写库（封存时落库）。
- 保证写入失败不影响主流程：维度落库异常只记日志、不阻断封存（降级）。
- **验收**：新封存一条记录后，查库可见 6 个维度全部落地；维度落库失败时封存仍成功。
- 完成后 commit：`feat(memory): 封存时持久化全部6个AI维度并做降级处理`

### Stage 0.3：历史数据回填脚本
- 写一个可重复执行的回填脚本（独立 main 方法 / 一次性接口 / 命令行任务均可，按项目习惯）：
  扫描"已封存但 5 维度为空"的旧记录，重新调用 DeepSeek 补全后写库。
- 必须**幂等**：已补全的记录跳过；支持限流/分批，避免一次性打爆 DeepSeek API。
- 提供 dry-run 模式（只统计待回填数量、不真正写库），先打印数量供人工确认。
- **验收**：dry-run 能正确报出待回填条数；正式跑后旧记录 5 维度被补全；重复跑不重复写。
- 完成后 commit：`feat(memory): 新增历史记录5维度回填脚本(支持dry-run与幂等)`

## 第 1 步：个人记忆 RAG 检索内核

### 背景与选型约束
- 这是 C 端小程序，数据量不大。**禁止为炫技引入重组件**。向量存储按以下优先级选型：
  1. 首选 `pgvector`（若项目用 PostgreSQL 或可接受挂一个 PG）；
  2. 次选已有/单机轻量 Milvus；
  3. 兜底：先用 MySQL 存向量 + 内存暴力余弦（数据量小可接受），把接口抽象留好。
- **关键设计**：检索维度不止"语义相似"，必须支持按**情绪标签 + 时间跨度**过滤召回。

### Stage 1.1：Embedding 与向量落库
- 为每条记录的 6 维度文本生成 embedding（用现有 DeepSeek/可接入的 embedding 接口；
  接口不可用时抽象出 `EmbeddingProvider` 接口 + 一个占位实现，便于后续替换）。
- 设计向量存储：记录 id、向量、关联的 emotion 标签、封存时间等可过滤元数据。
- 提供"对存量记录批量生成向量"的脚本（同样幂等、分批）。
- **验收**：新记录封存后自动生成并存入向量；存量记录可批量补向量；重复跑不重复。
- 完成后 commit：`feat(memory): 接入embedding并实现记录向量的生成与落库`

### Stage 1.2：检索服务（语义 + 情绪 + 时间过滤）
- 抽象 `MemoryRetriever` 接口，实现一个方法：
  `retrieve(query, topK, emotionFilter?, timeRangeFilter?)` →
  返回按相似度排序的记录列表（带分数）。
- 元数据过滤（情绪、时间区间）必须能与向量相似度结合（先过滤再算分，或算分后过滤均可，
  在注释里说明所选策略）。
- 写一个内部测试用例/接口，验证"找出过去所有'焦虑但最终释怀'类节点"这类查询能跑通。
- **验收**：给定一个查询能返回 topK 结果及分数；带 emotion/time 过滤时结果正确收窄。
- 完成后 commit：`feat(memory): 实现支持语义+情绪+时间过滤的记忆检索服务`

### Stage 1.3：对外检索接口（薄封装，不做前端）
- 暴露一个后端检索 API（Controller 层薄封装 `MemoryRetriever`），带鉴权、入参校验。
- **不做任何前端/小程序页面改动**，仅提供接口 + Swagger 文档便于后续联调。
- **验收**：Swagger 可见该接口；本地能调通返回结构化结果。
- 完成后 commit：`feat(memory): 新增个人记忆检索REST接口与接口文档`
