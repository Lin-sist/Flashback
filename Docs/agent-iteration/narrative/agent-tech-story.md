## §1 一分钟版本

**项目是什么**：《时光回序》Flashback，一个微信小程序日记产品。用户写下当下的情绪与困惑，把回答权交给时间，未来的自己重新理解这一刻。产品气质是安静、私密、克制——不是效率仪表盘，不是社交流，不是心理诊断工具。

**Agent 在其中承担什么**：一个被动召唤的共情友人。用户主动点开它才出现，帮用户把说不清的感受一层层问出来（情绪 → 困惑 → 核心问题 → 期望），记得用户三个月前写过什么，可以建议加标签或补正文但绝不代替用户封存。技术上是一个后端托管的单 Agent loop，不是前端调 API 的单轮问答。

**双项目分工**：我有两个 AI 项目，刻意分工——

| 项目 | 证明什么 |
|---|---|
| RAG 项目 | AI **知道**什么：检索、分块、可信、评测 |
| Flashback | AI **能做**什么：Loop、Tool、Memory、Guardrail、Trace、Eval、Reflection |

**技术栈**：Spring Boot 3.3.5 + MyBatis + MySQL 8.0 + Uniapp/Vue3 小程序；AI 侧走 OpenAI-compatible HTTP（DeepSeek），Agent runtime 全自研。

**当前进度**：Phase 1 六刀已归档（Runtime → Tool → Guardrail → Memory → Review → Observability），后端 534 tests PASS。Phase 2 四刀方向已冻结（Eval → Reflection → Resilience → Temporal）。

## §2 为什么自研 Loop，而不用 LangGraph / Spring AI

**一句话答案**：因为我的产品语义锁在阶段机里，而框架能给我的两样东西——可视化和 checkpoint——前者我不需要，后者我已经有了。

**怎么做的**

`AgentStageMachine` 是一个纯逻辑类（无 IO、无持久化、无 provider 调用）：

- 线性序列：`EMOTION → CONFUSION → CORE_QUESTION → EXPECTATION → CLOSING → ENDED`
- 两条抢占边：用户明确结束意图（关键词命中）、轮次达上限 → 直接进 `CLOSING`
- 一条自环：回避型极短回答时同阶段追问，**上限 1 次**，避免逼问
- `REVIEW`（友人回看）刻意不经此机器，传进来直接抛异常快速失败

**推进权在后端，不交给模型。**这是刻意的：「追问上限」「强制收束」「不逼问」必须能被单测钉死，交给模型就变成概率行为。

**为什么这样**

严格说，**这已经是一张图**——节点、边、抢占、自环、终态都在，只是用 `List` + `indexOf` 表达而不是 `Node`/`Edge` 类。所以「引入图框架」对我的增量收益只有：

| 框架收益 | 我的情况 |
|---|---|
| 通用节点图与可视化 | 六个节点的线性流程，不需要 |
| durable execution / checkpoint | 已有：会话与消息落 MySQL，可 resume ACTIVE 会话 |
| 社区示例 | 换不来产品语义 |

代价则是重写一套已测的阶段语义。**结论：留了 Port，没留框架。**

Spring AI 同理。我的请求形状已经是 industry shape(OpenAI-compatible messages + tools），框架是实现便利，不是能力解锁。而且 Spring AI 2.0 要求 Spring Boot 4.x + Framework 7，迁移得先做一次平台代际升级，风险叠乘。**更关键的一点**：迁移会同时吃掉我的 ToolRegistry、MemoryPort、护栏挂点、轨迹采集点——而这些恰好是我唯一能讲清楚也能逆向学习的部分。用框架换掉它们，我就从「作者」退化成「使用者」。

**我承认的代价**：自研意味着重试、多模态、流式这些都得自己写。如果哪天需要它们中的多数，迁移窗口才真正打开。

**证据**：`AgentStageMachine`（纯逻辑 + `AgentStageMachineTest`）、`agent_session` / `agent_message` 表、`AgentModelClient`。

## §3 工具调用怎么做的，为什么不做假降级

**一句话答案**：原生 function calling + 模型白名单门控 + 二段式确认；FC 不可用就退回纯对话，**绝不自己发明一套提议协议**。

**怎么做的**

- 协议用 provider 原生 FC，内部有 `AgentToolSchemaFactory` 生成 schema、`AgentToolValidator` 校验参数
- 可用性由**配置化的模型白名单**门控，不假设任意 OpenAI-compatible 模型都支持 FC
- schema strict 模式表达不了的约束（如正文最大长度）在代码层补
- 写操作**必须用户确认**：模型只能提议，前端弹确认条，用户点了才执行
- 工具执行结果（observation）回注下一轮上下文，窗口大小可配

**为什么这样**

「FC 不可用时用 prompt 模拟一套提议协议」是很常见的降级思路，我明确否决了。理由：那条路径会产出一个**看起来成功、实际是我自己解析出来的**工具调用。一旦它和真实 FC 混在同一个出口，我就无法回答「这次到底走的哪条路」。这撞在项目的一条硬规则上——**真实路径不得 mock success 冒充真实成功**。

**不做 MCP 内核化**：MCP 在 2026 已是工具互操作的事实标准，但我的工具是内生业务 API（草稿、标签、封存），没有外部消费方。现在 MCP 化只增加一层转换和一片安全面。所以 ToolRegistry 保持内部契约，MCP 列为**可选适配层**——需要时在 Registry 外面包一层，而不是反客为主。

**证据**：`agent/tool/*`(Registry / Coordinator / Validator / Executor）、`AgentModelClientToolCallingTest`、`agent_tool_call` 表。

## §4 护栏怎么判，为什么不用 LLM 审核官

**一句话答案**：确定性检查 + 忠实度双指标 + 按路径分流的降级；判定不交给第二个模型。

**怎么做的**

六类违规，每类带一个结构化短标识：

| 违规 | 判什么 |
|---|---|
| `UNFAITHFUL` | 增写了用户没表达过的内容 |
| `FABRICATED_QUOTE` | 引号里的「你说过」在原话中无出处 |
| `DIAGNOSTIC` | 在自己新增的表述里下诊断或给医学建议 |
| `FAKE_ACTION` | 谎称已代替用户封存 / 解锁 / 删除 |
| `MISSING_TIME_ATTRIBUTION` | 复述历史内容却没说清那是过去的事 |
| `CHECK_ERROR` | 判定器自身异常 → fail-closed |

**忠实度用双指标**：覆盖比例 + 最长连续未覆盖片段。单看比例会漏掉「大部分照抄、中间塞一句编造」;单看片段长度会误伤正常改写。两个一起才拦得住。

**降级按路径分流**，因为三条路径的失败成本不同：

- 工具提议 → **拒绝**(用户只是少看到一个确认条）
- 素材草稿 → **丢弃**(可选产物，复用「生成失败即 null」语义）
- 对话回复 → **替换为本地常量兜底**(用户提交了一轮，必须得到回应）

失败方向是刻意选的：**宁可少一个确认条、少一段素材，也不放行一句用户没说过的话进他的日记。**

兜底回复是本地常量，且必须留下结构化痕迹使其可与真实回复区分——**兜底不得伪装成模型正常输出**。

**为什么这样**

不用 LLM 审核官，三个具体原因：

1. **延迟**：实测 provider 单次 avg 6476ms。生成 + 审核 + 重写 ≈ 19.5s，直接撞死后端 20s 超时。
2. **可复现性**：LLM 判定不可复现，而我现在这套判定被几百个测试钉死，给定输入必然得到确定 violation。用不确定的换确定的，是净损失。
3. **隐私**：把用户回复连同原话送去给第二个模型打分，属于未授权外发。

**这里最容易被追打的一点我先说**：确定性检查能判「有没有越界」，判不了「好不好」。「听起来这段时间很难熬」和「你这是抑郁症的典型症状」的区别我能判（后者命中 `DIAGNOSTIC`)；但「这句共情够不够真诚」我判不了。**我没有假装能判**——见 §7。

**隐私设计**：判定结果 `AgentGuardrailVerdict` 是一个 record，只含 violation 类型 + 覆盖比例 + 最长未覆盖长度 + 受检字符数。**类型层就不接受文本内容**，因为它要进审计和日志。有一条专门的测试断言指标串不含原文片段。

**证据**：`agent/guardrail/*`、`AgentGuardrailBoundaryCaseTest`（五场景，每组含正例反例）、`verdictMetricsMustNotLeakContent`。

## §5 记忆分层怎么落地，为什么不上向量库

**一句话答案**：`MemoryPort` 抽象 + MySQL 关键词/标签/时间检索 + 有预算的注入；向量作为同一 Port 下的 v2 插件，不作为前提。

**怎么做的**

术语对齐业界的 multi-layer memory:

| 层 | 在我这里是什么 |
|---|---|
| Working | 当前会话的滑动消息窗口 |
| Episodic | 用户历史记录（检索命中的片段） |
| Semantic | 记录上的结构化摘要字段 |

检索：从近期消息抽关键词（有最小长度与数量上限）+ 标签 + 时间回溯窗口 → 命中片段。

**注入有预算**：条数上限、单片段字符上限，全部可配。不是「有多少历史塞多少」。

**注入的片段带时间元数据**，并且配了一条专门的护栏 `MISSING_TIME_ATTRIBUTION`：如果 Agent 复述了三个月前的内容却不说清那是过去的事，读起来就像用户刚说的话——**等于把三个月前的心情冒充成此刻的心情**。这是我在做记忆时最在意的一个失效模式，危害具体而非抽象。

**为什么这样**

不上向量库的理由不是「不会」，是**规模不匹配**：当前记录量级用 SQL 检索足以验证「它记得你」这个产品命题。提前上云向量库会让隐私边界、成本、本地开发、测试夹具全部变重，而换来的相关性提升在这个数据量上无法被证明。

所以做成 `MemoryPort`:`search(userId, query, filters, budget) → List<MemoryHit>`。检索从 LIKE → FULLTEXT → 旁路 embedding 都是同一个 Port 下换实现，不需要动编排层。

**我承认的短板**：现在是标签 + 说明性字段 LIKE,**没有权重、没有分词、没有向量**，相关性弱。这一条我在残留清单里明确记着（R9），没有粉饰成「够用了」。

**严格用户隔离**：所有检索按 userId 收口，不跨用户，后台也没有「全局扫描日记」的任务。

**证据**：`agent/memory/*`、`MySqlMemoryPortTest`、`MemoryCueExtractorTest`、注入预算配置项。

## §6 可观测性做了什么，发现了什么

**一句话答案**：每轮对话落一条 versioned 决策轨迹（thought → action → observation），不含任何原文；上线第一天就用它定位到一个让每轮卡满 50 秒的自锁缺陷。

**怎么做的**

一轮对话内的七八个采集点散落在编排的不同分支里。**我没有让每处各自 insert**，而是用一个 `AgentTraceCollector` 先收在内存，最后由唯一出口落库。理由很具体：provider 失败、护栏降级、fail-closed 丢弃这些**早退路径**最容易漏掉埋点，而那正是最需要痕迹的时刻。

采集的内容（全部是数值与枚举）：

- 阶段：from / to / reason
- 记忆：enabled / failed / hasCue / retrievedCount / injectedCount / injectedChars
- 上下文：messageCount + 各补充段是否存在
- provider:model / durationMs / mocked / success
- 工具：returned / proposed / discarded / rejectReason
- 护栏：每层 passed / violation / coverage / maxUncoveredRun
- 降级：layer / violation / fallback 是否本地常量
- 裁剪：beforeLength / afterLength

**隐私是靠类型系统守的，不是靠自觉**：收集方法只接受基础类型和既有枚举，**想把日记原文传进轨迹，在编译期就做不到**。少数 String 参数承载的是配置值、异常类名或结构化常量。

**版本锚点由内容哈希派生**：prompt 模板和护栏规则的内容变了，`prompt_version` / `policy_version` 自动变。这样「改文案前后的行为差异」第一次可以按版本分组比对。

**发现了什么（这部分是真正的收获）**

1. **provider 耗时首次有数据**：min 4571 / avg 6476 / max 8467ms。这项数据在此之前**完全不存在**——成功路径的起始时间被直接丢弃，只有失败路径才算耗时。有了它，我才发现前端 30s / 后端 20s 的超时设置里，后端留给 provider 的余量只有三倍中位数。

2. **一个我自己引入的严重缺陷**：轨迹落库用了 `REQUIRES_NEW` 想着「不影响外层事务」，结果每轮对话卡满 50 秒。根因：`REQUIRES_NEW` **挂起外层事务但不释放它已持有的锁**，新事务经外键去碰同一批 `agent_session` 父行，就和自己的外层事务死等到锁超时。

   **最值得说的是它怎么逃过测试的**：H2 上 37 项测试全绿。H2 没有 InnoDB 行级锁语义，**这个缺陷在 H2 上不可能复现**。修法不是换传播级别，是改用事务提交后的回调做副作用。

3. **一条反直觉的教训**：轨迹写入本身是 fail-open 的，失败不影响业务。但它在失败**之前**先卡了 50 秒。**fail-open 只保证不报错，不保证不阻塞**——评估「辅助设施失败会不会影响用户」时，必须同时看失败前的等待成本。

**诚实标注**：回看模式下的 fail-closed 分支（模型在无工具模式仍返回提议时丢弃），9 轮真实观察中**从未活体触发**，正确性目前只由单测覆盖。我把它记为未验证，没有写成「已验证」。

**证据**：`agent/trace/*`、`agent_turn_trace` 表、9 条排查 SQL、`AgentTraceCollectorTest`。

## §9 我知道但没做的，及理由

> 这一节是刻意写的。行业面试会考「什么时候某种编排是多余的复杂度」——**能论证不做，和能做出来同等重要。**

| 技术 | 不做的核心理由 | 翻案条件 |
|---|---|---|
| 图框架（LangGraph4j 等） | 现有状态机已具备节点/边/抢占/自环/终态；框架增量收益是可视化（不需要）与 checkpoint（已由 MySQL 会话实现） | 出现真正的并行分支与合并需求 |
| Spring AI 迁移 | 契约已是 industry shape;它要求 Boot 4.x + Framework 7，须先做平台代际升级；迁移会吃掉 Tool/Memory/Guardrail/Trace 四处自研资产 | 需要多模态 + 流式 + 重试中间件，自维护成本明显超过迁移成本 |
| LLM-as-Judge | 延迟撞超时 + 判定不可复现 + 日记原文外发需授权 | 有独立的、脱敏的、可复现的评测通道 |
| LLM 自检器 | 生成 6.5s + 自检 6.5s + 重写 6.5s ≈ 19.5s，撞死 20s 超时；用不确定判定替换确定性 checker 是净损失 | 判定延迟降到亚秒级 |
| 向量库 / GraphRAG | 当前数据量下 SQL 检索足以验证产品命题；上云向量库会让隐私、成本、本地开发、测试夹具全部变重 | 相关性问题可被量化证明，且 `MemoryPort` 下可插拔接入 |
| MCP 内核化 | 工具是内生业务 API，无外部消费方；只增加转换层与安全面 | 需要对外暴露工具生态 |
| 精细诊断载体（带文本片段的护栏诊断） | 靠后人自觉维持隐私边界不可靠——半年后有人为排查方便塞进 trace，红线就破了且无测试报警；要做得配约束测试，成本反超收益 | 有类型层面而非纪律层面的保证手段 |
| Multi-Agent / 用户可见多角色 | 破坏「一个朋友」的产品隐喻，且无产品需求 | — |
| 主动推送 / 情绪 dashboard / STT | 与「被动召唤」和「不诊断」的产品气质直接冲突 | — |
| 平台升级到 Spring Boot 4.x | 重心不在平台层；风险性质与业务刀不同——业务刀的风险是「设计对不对」可由测试回答，平台升级的风险是「哪个传递依赖不兼容」，工作量长尾不可预估 | Phase 2 完工后，或某刀确实需要 4.x 特性 |

## §10 踩过的坑

> 这一节是我认为最有价值的部分。能讲清一次真实事故的根因，比能背十个概念更说明问题。

### 10.1 H2 全绿不构成验证

轨迹落库在 H2 上 37 项测试全绿，却在真实 MySQL 上让每轮对话卡满 50 秒。H2 没有 InnoDB 行级锁语义，**该缺陷在 H2 上不可能复现**。

**改进**：凡涉及锁 / 外键 / 事务边界的改动，联调必须打真实 MySQL;写回归时优先断言**调用时机与不变量**而非结果，这样在 H2 上也能守住一部分。

### 10.2 `REQUIRES_NEW` 不等于「不影响外层事务」

它挂起外层事务，但**不释放外层已持有的锁**。新事务若要碰同一批行（尤其经由外键），就会与自己的外层事务死等。想做「业务提交后再做副作用」，该用事务同步回调，不是换传播级别。

### 10.3 前后端超时必须有明确先后，不能相等

两边都设 30s 时，前端总是先断，后端精心设计的显式失败语义被网络层错误覆盖，用户看到的是 `request: fail timeout`。定为前端 30s / 后端 20s,**顺序不可颠倒**。凡新增调用 AI 的前端请求，必须显式指定超时且大于后端上限。

### 10.4 规划期的「须同步 N 处」要在实现期复核

规划时我断言新表需要同步三份 schema，实现时发现全量脚本只维护到第一刀，项目既有约定与我的假设不符。**不要把假设写成事实。**

### 10.5 验证「拦截生效」前，先确认样本真的处于该被拦的状态

我曾取「最后一轮回复」做护栏剥离实验，而那一轮恰好没有复述历史内容，自然不该被拦。结论不翻转是**样本选错**，不是护栏失效。

### 10.6 主观感受会被无关变量污染

我曾判断「引导话术生硬」并准备去调 prompt。后来修掉一个 55 秒延迟缺陷，再体验就觉得「自然一些了」——而这期间**一行 prompt、一个阈值、一处引导策略都没改**。延迟污染了对语言质量的判断。

**这件事直接决定了我下一刀的顺序**：先建可回归的评测基线，再谈话术优化。否则只会得到第二个无法证伪的「感觉好了」。
