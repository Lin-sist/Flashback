# design.md 追加约束：决策记录（Decision Record）

> 用途：在每个 Type C change 的 `design.md` 中固定产出「决策记录」小节，  
> 供用户在事前闸门审查，并便于后续复盘 / 面试式追问。  
> 边界：**只写进 design.md**，不写进 `.ai/AGENT_LOG.md`（AGENT_LOG 保持纯执行证据）。  
> 来源：RAG 项目同名实践的 Flashback 本地化版。

---

## 对实现 / 规划 Agent 的指令

在 `design.md` 中新增一节：

```markdown
## 决策记录
```

为本 change 中**每一个存在真实岔路口的技术或产品决策**各写一条。

**判定标准**：只要「当时有两种以上合理做法、最终选了一种」，就必须记一条。  
纯粹唯一解、无取舍的实现细节不必记。

每条严格使用以下结构，**用大白话**，禁止贴大段代码：

```markdown
### 决策 N：<一句话描述这个决策点>

1. **面临的选择**：列出 2–3 个当时真实存在的候选方案（含最终被否决的），每个用半句话说清它是什么。
2. **选了哪个 + 为什么**：写明选定项，并给出决定性理由（职责边界 / 一致性 / 风险 / 与既有 OpenSpec 兼容 / 产品气质等）。
3. **放弃的代价**：说明被否决方案各自的具体代价，即「如果选它会发生什么糟糕的事」。
```

---

## 硬性要求

1. 决策必须是**本 change 真实发生**的取舍；凡不确定的写「待用户在事前闸门确认」，**不得编造备选方案凑数**。
2. 每条决策必须可被一个「为什么不……」的追问检验；写完自检：若问「你为什么不选另一个方案」，本条是否已给出答案。
3. **不**复述 proposal 的用户故事，**不**复述 spec delta 的整段契约；本节只承载「取舍理由」。
4. **out_of_scope 的边界决策**也必须各记一条（例如「为什么 M4 不做语音转写」「为什么 Agent 首版不做自动封存」）——「刻意不做什么」往往是最高频追问点。
5. 涉及用户日记、位置、附件时，若存在「是否记录原文到日志/模型侧缓存」等分岔，必须单独成条，并默认倾向**最小暴露**。
6. 与已有 `backend-contract-decisions.md` 类文件的关系：
   - **契约决议**（字段名、枚举、错误码）→ 可留在 contract decisions；
   - **工程/产品取舍**（为什么用状态机而不是一次 prompt、为什么 tool 白名单如此）→ 必须进本节。

## Flashback 常见决策主题示例（按需，勿硬凑）

- AI：真实 provider vs 仅 mock；失败 FALLBACK vs 硬错误；超时预算。
- 媒体：七牛 vs S3-compatible 配置边界；私有桶与验活；封面是否仅来自已有图片。
- 封存：不变性落在后端强制 vs 仅前端禁用。
- Preview：隔离策略（独立 store / 路径守卫 / API 拒绝）。
- 未来 Agent：单轮工具调用封装 vs 多轮 runtime；Memory 用关键字 vs 向量；主动提醒 vs 仅被动。

## 最小合格示例（示意）

### 决策 1：封存后附件变更拦在哪一层

1. **面临的选择**：仅前端禁用编辑入口；仅后端接口拒绝；前后端双拦。
2. **选了哪个 + 为什么**：前后端双拦。前端负责体验，后端是权威，防止直接调 API 绕过。
3. **放弃的代价**：只拦前端则契约可被绕过；只拦后端则用户先完成操作再失败，体验差且易产生脏请求。
