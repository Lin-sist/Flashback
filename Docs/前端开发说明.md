# 《时光回序》前端开发说明（微信小程序 MVP）

本文档用于约束《时光回序》用户端前端开发方向，服务于以下目标：

1. 固定当前 MVP 的前端形态、页面范围和交互边界
2. 为 Copilot 提供可执行的开发约束，避免擅自扩功能或换技术路线
3. 为 Figma、Google Stitch、v0 等 AI 设计工具提供统一提示词边界
4. 让前端实现与现有后端、数据库和业务规则保持一致

---

## 1. 当前项目状态

### 1.1 已完成部分
- 后端 MVP 主链路已具备基础能力，可支持前端开始开发
- 当前已存在用户、记录、回信、标签、AI 辅助等用户端接口
- 后端已统一鉴权方式、统一返回体、统一异常处理
- 数据库设计、接口清单、MVP 范围文档已经基本齐备

### 1.2 当前未完成部分
- 用户端前端工程尚未正式初始化
- 小程序视觉规范、页面结构和组件规范尚未收敛成一份专门文档
- 微信登录、订阅消息授权、生产级提醒链路还未完整接入

### 1.3 当前前端工作的目标
当前前端工作的目标不是“自由发挥做一个情绪产品”，而是优先完成 MVP 用户主链路：

`登录 -> 首页 -> 新建/编辑记录 -> 封存 -> 我的记录 -> 解锁回看 -> 可选回信 -> 时间轴 -> 个人中心`

## 3. 固定技术路线

### 3.1 用户端技术栈
- 前端形态固定为：`微信小程序`
- 开发框架固定为：`Uniapp`
- 页面语法固定为：`Vue 3 composition API 风格`
- 状态管理建议：`Pinia`
- 网络请求建议：封装统一 `request` 层，统一处理 `token`、错误码、登录失效

### 3.2 当前不采用的方案
- 不做响应式 Web 版本作为用户端主实现
- 不做 H5 优先再迁移小程序
- 不做 React Native、Taro、原生小程序双栈并行
- 不将管理端与用户端放在同一个前端工程中

### 3.3 推荐工程目录
建议按以下思路搭建前端工程：

- `src/pages/`：页面
- `src/components/`：复用组件
- `src/layouts/`：页面容器与导航外壳
- `src/stores/`：用户态、记录态、标签态
- `src/services/`：接口封装
- `src/types/`：接口类型与业务枚举
- `src/constants/`：状态枚举映射、文案常量、缓存 key
- `src/utils/`：时间格式化、状态映射、请求封装

## 4. MVP 页面范围

### 4.1 必须实现页面

| 页面 | 目标 | 说明 |
| ---- | ---- | ---- |
| 登录/注册页 | 完成用户鉴权 | 第一版先走账号密码链路 |
| 首页 | 提供主入口和最近解锁提醒 | 强调“新建记录”和“最近抵达” |
| 新建/编辑记录页 | 完成草稿创建、AI 辅助、封存 | 这是核心业务页 |
| 我的记录页 | 查看草稿、已封存、已解锁记录 | 支持筛选与分页加载 |
| 记录详情页 | 根据状态展示不同内容 | 草稿详情与解锁详情可以复用一套页面骨架 |
| 回信页或详情内回信区 | 对已解锁记录写一句回信 | 第一版只支持一条回信 |
| 时间轴页 | 按时间查看历史记录 | 用于形成“人生节点回看”感 |
| 个人中心页 | 查看和修改资料 | 只做基础资料维护 |

### 4.2 可以合并实现的页面
- “新建记录页”与“编辑记录页”可复用同一页面
- “解锁详情页”与“记录详情页”可基于状态差异做条件渲染
- “回信页”可以做成详情页内的一个固定模块，而不是独立路由

### 4.3 当前明确不做的页面
- 广场页
- 社交关系页
- AI 对话页
- 多媒体上传页
- 成长报告页
- 公共分享页
- 管理端页面

## 5. 核心业务规则

### 5.1 记录状态只能有三种
- `DRAFT`
- `SEALED`
- `UNLOCKED`

状态流转固定为：

`DRAFT -> SEALED -> UNLOCKED`

### 5.2 前端必须遵守的状态行为
- `DRAFT`：允许编辑、删除、继续调用 AI 辅助
- `SEALED`：只读展示，不允许编辑、删除
- `UNLOCKED`：允许查看全文和可选回信

### 5.3 回信规则
- 回信不是强制动作
- 每条记录第一版只允许一条回信
- 只有 `UNLOCKED` 状态才允许回信
- 回信提交后不可编辑、不可删除

### 5.4 AI 规则
- AI 只是辅助，不得成为主流程依赖
- 当前只允许两种 AI 能力：
  - 写作提示 `writing-prompts`
  - 内容整理 `summarize-record`
- AI 失败时前端必须允许用户继续手动写作和保存草稿

### 5.5 隐私规则
- 所有记录默认私密
- 不提供公开列表、推荐流、点赞、评论、转发
- 不允许前端设计出“别人也能看到你写了什么”的暗示性交互

## 6. 现有后端接口基线

以下接口已经具备，可直接作为当前前端 MVP 的联调基础：

### 6.1 认证与用户
- `POST /api/auth/register`
- `POST /api/auth/login`
- `GET /api/user/me`
- `PUT /api/user/profile`

### 6.2 记录主链路
- `POST /api/records`
- `PUT /api/records/{id}`
- `DELETE /api/records/{id}`
- `POST /api/records/{id}/seal`
- `GET /api/records`
- `GET /api/records/unlocked`
- `GET /api/records/timeline`
- `GET /api/records/{id}`

### 6.3 回信
- `POST /api/records/{recordId}/reply`
- `GET /api/records/{recordId}/reply`

### 6.4 标签
- `GET /api/tags`

### 6.5 AI 辅助
- `POST /api/ai/writing-prompts`
- `POST /api/ai/summarize-record`

### 6.6 统一接口规范
- 所有用户端接口统一返回 `ApiResponse<T>`
- 成功时：`code = 0`
- 鉴权方式：`Authorization: Bearer <token>`
- 分页默认参数：`pageNum = 1`，`pageSize = 10`

## 8. 页面交互约束

### 8.1 登录/注册页
- 第一版只做账号密码注册登录
- 登录成功后保存 token，并拉取或同步 `userInfo`
- 不要在这一步加入微信登录、短信登录、多因子登录

### 8.2 首页
- 首页主 CTA 必须是“新建记录”
- 首页次重点是“最近已解锁记录”或“最近抵达”
- 首页不是信息流，不要做瀑布流、推荐卡片、社区动态

### 8.3 新建/编辑记录页
- 必须支持标题可空、正文必填、记录类型、核心问题、标签、解锁时间
- AI 按钮要清晰标注为“辅助整理”或“给我一点提示”，不要伪装成自动写作
- 保存草稿与封存操作必须明确区分
- 封存前要二次确认，强调“封存后不可修改”

### 8.4 我的记录页
- 默认按状态分栏或筛选
- 优先支持：
  - 全部
  - 草稿
  - 已封存
  - 已解锁
- 列表重点展示：
  - 标题
  - 内容摘要
  - 状态
  - 时间信息
  - 标签

### 8.5 记录详情页
- `DRAFT` 详情页应保留继续编辑入口
- `SEALED` 详情页应强调“等待抵达”的状态感
- `UNLOCKED` 详情页应强调阅读沉浸感和回信入口
- 详情页不要变成复杂表单页或聊天页

### 8.6 回信区
- 回信输入区要克制，强调“一句回应”而不是长篇续写
- 已有回信时，展示结果，不再开放重复提交入口

### 8.7 时间轴页
- 时间轴按 `yearMonth` 分组即可
- 第一版重点是“回望感”，不是数据分析
- 不做热力图、复杂统计图表、成长雷达图

### 8.8 个人中心页
- 只做：
  - 查看当前用户信息
  - 修改昵称、邮箱、头像
  - 退出登录
- 不做复杂设置中心

## 9. 视觉与体验方向

### 9.1 产品气质
《时光回序》不是效率工具，也不是社交产品，它的气质应该是：
- 安静
- 克制
- 私密
- 温柔
- 有一点仪式感

### 9.2 体验关键词
视觉和交互需要围绕这五种体验组织：
- 写下当下时的郑重感
- 封存之后的等待感
- 到期解锁时的抵达感
- 回看旧文字时的时空错位感
- 给过去自己一句回应时的释然感

### 9.3 设计倾向
- 以卡片、留白、时间感为主，不要做花哨社交 UI
- 可以使用纸张、邮局、时间胶囊、档案卡等隐喻
- 颜色以低饱和、温暖或清冷的时间感色系为主
- 动效应少而准，服务于“封存”“抵达”“展开阅读”

### 9.4 明确不要的风格
- 不要做成社交社区 App
- 不要做成任务清单 App
- 不要做成强心理疗愈问卷产品
- 不要做成“AI 陪聊机器人”界面
- 不要用过强的赛博、荧光、游戏化视觉语言

## 10. Figma、Google Stitch、v0 使用说明

这些工具可以辅助你提效，但不能替你决定产品边界。

### 10.1 允许它们做的事
- 输出页面信息架构
- 生成低保真线框图
- 生成页面布局初稿
- 提供配色、版式、组件层级灵感
- 快速探索“安静、私密、时间感”的视觉方向

### 10.2 不允许它们做的事
- 擅自增加新页面和新模块
- 将产品改造成社交平台
- 自动加入聊天机器人主流程
- 自动加入图片上传、音视频、公开广场、成就系统
- 重新定义记录状态或回信规则

### 10.3 给 Figma / Stitch / v0 的固定约束
每次生成前端页面时，都应附带以下约束：

- 产品名：`时光回序`
- 端形态：`微信小程序`
- 框架目标：`Uniapp + Vue 3`
- MVP 页面范围固定，不新增页面
- 主流程固定为：`写下当下 -> 封存 -> 到期解锁 -> 回看 -> 可选回信`
- 记录默认私密，不做社交广场
- AI 只做辅助提示，不做聊天主流程
- 风格偏安静、克制、私密、时间感

### 10.4 可直接复用的页面生成提示词

#### 首页提示词
`请为“时光回序”设计一个微信小程序首页。产品是一个私密的时间记录产品，主流程是写下当下、封存记录、到期解锁回看。首页重点突出“新建记录”和“最近已解锁内容”，风格安静、克制、温柔，带一点时间感和仪式感，不要社交化，不要信息流，不要聊天机器人。`

#### 新建记录页提示词
`请为“时光回序”设计一个微信小程序的新建记录页面，支持标题、正文、记录类型、核心问题、标签、解锁时间，并提供 AI 写作提示和 AI 内容整理两个辅助入口。请突出“保存草稿”和“封存记录”两个动作，强调封存后不可修改。页面应私密、专注、克制，避免复杂装饰。`

#### 记录列表页提示词
`请为“时光回序”设计一个微信小程序的“我的记录”页面，支持按状态查看草稿、已封存、已解锁记录。每条记录展示标题、内容摘要、时间、状态和标签。风格安静、清晰、具有时间归档感，不要做成社区动态列表。`

#### 解锁详情页提示词
`请为“时光回序”设计一个微信小程序的记录详情页，场景是用户在未来某一天重新阅读过去封存的文字。页面需要突出阅读感、时间抵达感和可选回信入口，避免编辑态表单感，不要做成聊天界面。`

#### 时间轴页提示词
`请为“时光回序”设计一个微信小程序时间轴页面，用于按年月回看自己的历史记录。页面应该传达“人生节点档案”的感觉，强调回望，而不是数据分析。不要复杂图表，不要社区元素。`

## 11. 给 Copilot 的前端生成约束

### 11.1 技术约束
- 用户端只能生成 `Uniapp + Vue 3` 代码
- 不要生成 React、Next.js、纯 H5 SPA 作为主实现
- 不要把前端写成 Web 管理端模板

### 11.2 范围约束
- 不要新增广场、评论、点赞、私信、关注
- 不要新增图片、语音、视频上传
- 不要新增 AI 对话页面
- 不要新增成就系统、积分体系、任务体系

### 11.3 接口约束
- 前端只调用已有后端接口
- 不要在前端直接调用模型 API
- 不要在前端存储 AI provider key
- 所有请求走统一请求封装

### 11.4 状态约束
- 记录状态只能处理 `DRAFT / SEALED / UNLOCKED`
- 回信只能处理“一条已提交回信”这一 MVP 模型
- 不要自行发明 `ARCHIVED`、`PUBLISHED`、`LOCKED` 等新状态

### 11.5 UI 约束
- 页面要围绕“记录与回望”设计
- 不要滥用浮夸插画、游戏化徽章、夸张渐变
- 不要把首页设计成推荐流
- 不要把解锁详情设计成聊天对话气泡

## 12. 推荐开发顺序

建议按以下顺序推进前端工程：

1. 初始化 Uniapp + Vue 3 工程
2. 完成路由、页面骨架、请求层、登录态管理
3. 接通登录/注册/当前用户信息
4. 接通标签接口与基础枚举映射
5. 完成新建/编辑记录页
6. 完成我的记录页和详情页
7. 完成封存流程与解锁后的阅读态
8. 完成回信功能
9. 完成时间轴页
10. 完成个人中心页和整体视觉收口

原因：
- 登录态和请求层是所有页面的基础
- 记录页是核心价值页，优先级最高
- 时间轴和视觉收口适合放在主流程打通之后

---

## 13. MVP 验收标准

当前前端完成后，至少要满足以下标准：

1. 可以完成注册、登录、退出登录
2. 可以创建草稿、编辑草稿、删除草稿
3. 可以封存记录并清楚看到“封存后不可修改”
4. 可以看到我的记录，并按状态区分
5. 可以查看已解锁记录详情
6. 可以对已解锁记录写一句回信
7. 可以在时间轴页回看自己的记录
8. AI 失败时不影响用户继续写作和保存
9. 页面风格与产品气质一致，没有出现社交化偏航

## 15. 下一步建议

为了让前端推进更顺，建议你接下来按这个顺序准备：

1. 先用 Figma 做低保真信息架构和页面流转图
2. 再用 v0 或 Stitch 探索单页布局方案
3. 确认风格后再让 Copilot 生成 Uniapp 页面代码
4. 代码生成时始终附上本文档和 `Docs/MVP开发说明.md`
5. 联调时以当前后端代码返回字段为准，不依赖想当然字段

如果后续你开始初始化前端工程，这份文档就应该作为用户端前端开发的总入口文档。
